## J1 — Product slice, domain and monetary semantics

First gate proves ledger itself using synthetic controlled account administration and authorized synthetic financial command fixtures. Includes immutable currency/book/account configuration, opening zero-balance accounts, local journal posting, replay, reversal, status/close, reads, event production/order, verifier and actual restore. No real funds, customer money route, generic raw journal API, external provider, customer approval implementation, fee quote, FX group, Treasury, settlement, Redis/broker or speculative shared services. A standalone fixture is not product account activation or permission to deploy. Keep Identity-first/platform gate; if current authorization not available, run only isolated fixture with explicitly provisioned synthetic authority, no enabled runtime posting. No replacement of actual security evidence by mock. Candidate chart in [evidence A](ledger-cross-border-evidence.md#deep-dive-a--financial-accounting-and-ledger-domain-model), owner must accept actual account types and floors.

Single synthetic book (accounting boundary, not tenant); explicit book key and immutable currency version (code, exponent, reference version). No cross-book or cross-currency journal. Versioned currency records immutable; enabling/disabling new accounts is separate administration. Existing balances/records never reinterpreted when currency metadata changes. For initial fixture USD exponent 2, no FX arithmetic. Account normal side D/C, accounting class ASSET/LIABILITY/EQUITY/REVENUE/EXPENSE, opaque owner reference, immutable type/version, explicit nullable floor (NULL = unrestricted only with approved policy; ordinary customer liability and cash floor zero), status ACTIVE/SUSPENDED/CLOSED, current normal-side signed int64 balance and nonnegative monotonic account sequence. Candidate initial types: collection cash asset, capital equity, customer available liability; other chart types only when accepted use case. Opening balance zero and sequence zero; funding through balanced journal, no seed balance UPDATE. Customer ownership/tenant mapping distinct from book; ledger stores necessary trusted opaque resource/tenant binding when applicable; no direct Accounts/Identity FK or join. Closed readable; no reopen/reuse in first slice. Ledger-owned freeze fence denies new applicable money effects; future external recognition/hold resolution uses distinct accepted templates, not generic bypass. First slice has no external effects or hold obligations; do not claim safe financial account closure with external obligations until future guards implemented.

Entry amount positive bigint in range 1..9223372036854775807, direction D/C. Balance delta for normal side = amount if direction equals normal side, otherwise negative amount. A journal has at least two entries, one book and currency version, sum(D)=sum(C) exactly, no aggregate across currencies. Multiple lines for same account permitted candidate; net per account calculated before final floor check, sequence advances once for that account for the journal (including zero net delta). No implicit netting across journals. Negative balance only with explicit floor policy. Exact intermediate totals/deltas (Go big.Int or independently reviewed checked arithmetic, PostgreSQL numeric constrained by operation limits); only stored amount/balance/sequence cast to int64 after bounds check. Do not negate int64 minimum in Go or assume sum fits int64. Candidate engineering limits for review, not active requirements: max 64 entries per journal, max 128 UTF-8 bytes per opaque key/reference, bound structured command payload at facade/repository; choose exact wire bounds during acceptance. Preserve ordered entry positions; no sorting caller payload to change semantics.

Synthetic USD cents fixture: seed D cash 100000 / C capital 100000; fund D cash 10000 / C Alice liability 10000; transfer D Alice 4000 / C Bob 4000; reverse D Bob 4000 / C Alice 4000. Cash stays 110000 after transfer/reverse; capital 100000; Alice goes 10000→6000→10000, Bob 0→4000→0. Distinct journal IDs, reversal references original. The funding assumes synthetic confirmed cash; never create customer liability without approved economic template. This is illustrative accounting, not revenue/legal policy.

## J2 — Relational model and enforceable constraints

Logical names under proposed owned schema mamony_ledger (no SQL migration authored). UUID IDs candidate, stable caller/operation keys bounded text (byte limits, deterministic collation or canonical ASCII for IDs); record times timestamptz from DB, not commit order. Every required field NOT NULL unless explicitly optional. PK/FK/unique/check defined in migration; constrain text enums rather than silently accept arbitrary values. Indexes are candidate minimum, verify actual query plans and workloads. No partitioning or sharding before evidence.

Candidate no duplicate stored journal totals (derive from entries), no account delta cache outside Ledger. Journal request and journal relation must be proven 1:1 at commit (claim->journal FK and unique journal link; consider reciprocal deferred FK or a narrow independently justified constraint; Go transaction must write both and verifier detects missing). A simple SQL CHECK is row-local, cannot establish journal aggregate balance or every entry's semantic validity. Composite FKs prevent mixed book/currency; Go repository validates the complete journal with pure domain rules and current locked state before writing. Use database declarative constraints for row/relationship invariants. A narrowly scoped trigger or function is an exception only when an explicit invariant/threat requires it and independently reviewed, not the default posting path. Historical immutability: deny UPDATE/DELETE/TRUNCATE of journal, entry and step history to runtime; schema owner/superuser can change DDL and remains trusted Profile A. Ledger writer can INSERT history and UPDATE specifically granted balance/state columns and can therefore bypass Go cross-row/template checks if misused; do not claim SQL-level enforcement of every monetary invariant. Catalog tests must show permitted and denied DML, including other capability roles, read-only verifier and relay. Verifier detects inconsistency, not prevention of a compromised writer.

Migrations: extend existing versioned SQL-only golang-migrate runner only after accepted ledger slice; separate ledger migration history/fingerprints, roles and forward-only applied files. No automatic migrations at HTTP startup. Proposed order: isolated schema/roles & ownership, reference/account tables, posting structures/constraints, owned repository operations/grants, event/admin structures when used, tests on fresh and supported upgrade. Use existing fingerprint convention, not hand-edit applied fingerprint. Record dirty state and recovery, never silently drop history; rollback deployment by disabling capability, forward correction for money. Real migration plan and exact DDL depend on approved design; no new files in db/migrations in this PR.

## J3 — Database and caller authority

**Owner-selected Option A: Go repository with direct parameterized SQL, not a stored posting procedure.** Go domain owns deterministic money rules; usecase owns authorization and commands; ledger repository owns the full local transaction, lock acquisition, replay, domain calculation against freshly locked records, writes and error classification. No duplicated procedural posting rules in PL/pgSQL. Dedicated limited Ledger writer login/pool (never schema owner, migrator, superuser or BYPASSRLS); grant only required SELECT/INSERT and column-scoped UPDATE, including balance/sequence or approved status fields as needed. Immutable journal/entry/step/request/event history: INSERT/SELECT only as needed, no UPDATE/DELETE/TRUNCATE. If a guard or SELECT FOR UPDATE requires UPDATE privilege, review the exact required privilege and its consequences; do not grant blanket table write to obtain locks. Reference/account configuration administration separated where practical; verifier/read/relay roles restricted to necessary reads/progress. No role escalation, PUBLIC data access, cross-owner business DML/joins/FKs, shared transaction, unsafe dynamic SQL, or handler exposure to pool. Keep SQL parameterized, schema-qualified and versioned in Go source; only schema/constraint/grant changes require a migration. Actual catalog/grant and connection tests required; exact privilege matrix still pending G3. Trusted caller from composition/identity authority under Profile A, not HTTP string/GUC; DB login restricts storage rights but does not authenticate business caller. A compromised or erroneous Ledger writer can write a structurally valid but economically wrong journal, update balances without a journal, or insert incomplete history where constraints cannot prohibit it. This residual risk is explicit, not resolved by verifier or static checks; if prevention against a malicious scoped writer becomes mandatory, revisit restricted DB mutation or independent authority by ADR before enabling affected scope. First scope only approved synthetic templates and narrow service scope, no public or customer money path, no fixture authorization in deployment. Later operation-bound permit and freeze currentness still require approval and tests. No claim of database-owner/full-process compromise resistance. No secrets/PII in canonical keys, logs or events.

## J4 — Command and posting protocol

Illustrative typed facade operations (not Go declarations): OpenAccount, GetAccount/Balance, PostApprovedJournal (internal approved synthetic template only), GetPostingResult, ReverseJournal, SuspendAccount, CloseAccount, ListAccountEntries. Reference/currency administration only through designated controlled commands, no public API. Close and suspend exact owner scope; replay of already committed command uses current read authorization rather than current mutation eligibility. No Hold/Capture/Release, FX group or external permit APIs until their slices. Internal call carries authenticated service authority, tenant/resource scope, command ID, business/economic fact reference, book/currency version, template ID/version, ordered validated entry content, applicable approval binding and stable correlation metadata. Caller cannot choose arbitrary raw account/direction for a template. Template validates allowed classes, owner relation, operation and amounts, not just debit=credit. For fixture funding/transfer/reversal, designated synthetic command and account binding must be explicitly accepted; reversal server derives exact opposite ordered entries from original, not supplied by caller. Reversal-of-reversal decision: candidate refuse first slice; requires explicit acceptance, not new general correction.

Replay: preserve LGR-03 caller/key; canonical version and complete ordered typed content, including scope, book/currency, template, economic fact, accounts, directions, amounts, reversal and immutable authorization/intent binding if applicable. Exclude volatile transport/correlation/attempt timestamps and receipt presentation; store first correlation for trace. Define byte encoding (candidate length-prefixed UTF-8/ASCII identifiers and fixed-width signed integer canonical representation, no float/ambiguous JSON). Go owner constructs canonical bytes and digest from validated typed fields, never trusts caller-provided digest alone. Database stores exact bytes and uniqueness constraints; no claim that DB independently recomputes semantic content. Store exact bounded canonical bytes or canonical typed manifest plus SHA-256; equality requires exact content, not just hash. Version golden vectors before code. Fact namespace assigned from trusted authoritative economic owner/type/scope; different caller keys for same economic fact conflict unless separately authorized distinct effects defined. Fact conflict does not disclose another owner's journal. Return same committed journal/event identity only to authorized replay caller. Known refusal leaves no new committed posting; durable security audit/refusal handled separately per policy.

Owner-local transaction sequence:
1. Bound/validate shape and authenticated caller, template, exact allowed scope before DB work; preallocate journal ID only for candidate new claim; never disclose before commit.
2. Begin explicit READ COMMITTED on ledger-owned connection. Claim posting key + unique economic fact in one insert (no committed pending claim). Concurrent collision waits then resolve using subsequent statement snapshot: equal same key -> verify exact content and authorized read, return stored durable result; changed key content or economic fact under different key -> typed conflict. If conflicting fact and no authorized matching key, no result disclosure. Use tested SQL shape; do not assume single-statement CTE sees conflicting committed row. New claim rolls back on any refusal. No separate committed replay row.
3. For reversal, claim original under unique reversal constraint/appropriate lock; derive original immutable entries and validate eligible original; no external query. Lock required ledger-local lifecycle/obligation guards and all distinct account rows in stable sorted immutable account ID order; if account set changes, abort/replan. Read current status/book/currency/type/floor/balance/seq under locks. Open/close/freeze and account updates serialize with same local guard/rows. Account types immutable. No SKIP LOCKED for financial account locks, no stale projection or network call. Check applicable permit/authority fence only when actually implemented; protected flow remains disabled until then.
4. Invoke the same pure Go domain calculation against locked account state; revalidate approved posting template, all amounts, entry count, exact sums, account net deltas, final signed int64 balance and approved floor, seq increment bounds. Refuse whole journal if any failure. Sum in exact wide intermediate type; per-account zero delta still gets sequence step. No negative floor bypass for reversal or privileged fixture.
5. Insert immutable journal, entries, one step per touched account with before/delta/after and sequence, update owned account balances and counters, insert one immutable outbox event and dependencies for all affected accounts. Verify constraint completeness. Commit once; no foreign capability effects. If event or any write fails, rollback all. Return durable result only after known commit; preserve unknown outcome if commit reply absent.
6. Known SQLSTATE 40001/40P01 or proven no-effect abort -> bounded whole-operation retry using same key under current admission/deadline policy. Lock timeout/cancel classification must be tested; not all context/network errors prove rollback. Unknown commit -> query/replay same key under authorized result recovery, never new key. Distinguish result not found at a point in time from permanent no-effect fence. No automatic retry of denied financial command with changed identity. Stable typed errors: invalid, forbidden, not found (safe disclosure), key/fact conflict, closed/suspended, floor, range, retryable known abort, outcome unknown, unavailable/integrity incident. No raw SQL to consumer. Local lock ordering reduces deadlocks; actual FK/index/unique lock graph and implicit lock behavior must be proven, not assumed from model.

PostgreSQL 18 references checked 2026-11-24: [constraints](https://www.postgresql.org/docs/18/ddl-constraints.html) (CHECK not cross-row), [isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [consistency checks](https://www.postgresql.org/docs/18/applevel-consistency.html), [SELECT locking](https://www.postgresql.org/docs/18/sql-select.html) (SKIP LOCKED not a consistent financial read; queue use only). Repo DEC-01 pins PostgreSQL 18.7, Go 1.27, pgx v5; exact real tests required. Existing pool default BeginTx uses database default isolation; explicit approved isolation must be enforced/tested, not assumed from server settings. No global transaction coordinator.

No usecase imports pgx, no generic callback exposing tx. Composition wires public facade and capability authority; app cannot import private internals. Do not duplicate domain formulas in SQL; apply validated deltas through constrained writes, verify affected row counts and returned state. Actual repository persisted results must agree with an independent arithmetic oracle, not the same implementation used to calculate expected output. Query-only changes deploy with Go binary, while incompatible schema changes require expand/contract and mixed-version integration review. No cross-owner local transaction handle. Runtime worker/relay composition only when gate reaches it; no empty future folders.

## J6 — Reads, outbox and verifier

Balance query from authoritative primary (strong read after acknowledged posting), exact account status and sequence in same snapshot. Statements use ordered (account_seq,entry_position), captured per-account high-water seq from first authorized read; subsequent pages <= high-water and > last tuple. Immutable account step/entries, stable keyset cursor bound to account/scope/filter/watermark; verify cursor integrity and authorize every read. Opening/closing normal-side amount can derive from step before/after; if same journal has multiple entries, intermediate line ordering/display semantics explicit, final floor per journal, not pretend intermediate lines are separately committed balances. Multi-account consistent read requires one snapshot; no global commit order from sequence IDs or record timestamp. No direct foreign owner SQL. Read-only verifier in repeatable-read snapshot recomputes exact per-currency journal debit/credit, ordered steps before/after and final accounts, replay/fact cardinality, reversal and outbox coverage, dependency chains; report drift, never auto-adjust or mutate financial records. Large scan batching/snapshot resource policy must be measured; first fixture bounded. Report accessible only authorized verifier/operator, alert when failed/stale.

Event ordering: each journal has one event with all touched account sequences and predecessor dependencies. Relay only eligible when each predecessor for same consumer is durably acknowledged (or justified retained checkpoint). One consumer must not publish later overlapping-account event while earlier one unresolved; independent account/consumer paths can progress. Claim queue rows using appropriate local transaction and bounded lease; SKIP LOCKED only for eligible queue jobs, never skip required predecessor. Publish outside DB; lost ack -> original event ID redelivery; consumer inbox + local effect/progress atomic where required. Late duplicate older event may arrive, consumer dedups; guarantee applies to first accepted effect/order, not physical network exactly-once. Poison events block dependent paths, alert, no arbitrary skip. Retain unpublished history and durable replay key lifetime; DEC-10 controls published retention, predecessor checkpoint and rebuild from immutable journal history, not short outbox. Do not delete prerequisites still needed. Initial event creation gate before advanced relay, ledger gate requires actual relay/order/restore.
