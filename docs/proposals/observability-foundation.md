- **Issue / decision owner / technical reviewer:** No issue opened for this proposal. Repository owner owns product decisions. Independent technical review is pending.
- **Status:** PROPOSED
- **Risk path and rationale:** Critical. Request and worker correlation crosses trust boundaries, and telemetry may disclose identity or financial information or leave the application through an exporter.
- **Affected contracts and requirement IDs:** Platform FND-04, FND-10, FND-11 and FND-12; HTTP contract in ADR-0003; package boundaries in architecture and conventions.

## G1 — Research and problem validation

**Current behavior and problem:** The `main` snapshot at `f3896e8bcc0bfdea431ce0e986abd7231c24b3cc` configures JSON `log/slog` in `cmd/mamony` and several independent Identity commands. The application passes a logger to the HTTP composition root. The default process serves health routes only. No OpenTelemetry, Prometheus or GoMock dependencies were found in `go.mod`. Existing Identity use-case tests use explicit fakes. The repository's FND-04 contract requires structured logs and correlation across a request, job and consumer. The current logging setup alone does not provide trace context, a telemetry export path or proof across an asynchronous boundary.

A safe synthetic HTTP-to-worker path exists in `TestIdentityZBrowserVerificationE2E`: a test-only loopback TLS mux receives an unmounted registration request, PostgreSQL stores the encrypted proof-delivery outbox row, the bounded worker sends to a local Mailgun HTTP mock, and the test drives email confirmation. `TestIdentityMailgunMockPipeline` separately checks outbox retry and the facade runner against disposable PostgreSQL and the same local mock. These tests keep production routers health-only and perform no external email sends. They make this a viable observability test path. They do not currently prove trace correlation. The handler and enrollment flow expose only an opaque receipt/error, the proof issuer discards the generated challenge ID from its return value, and the consumer later receives that challenge ID from PostgreSQL. No request context or correlation value is currently persisted for producer-to-consumer tracing. A stand-alone trace fixture remains insufficient for FND-04.

## G2 — PRD / accepted requirements

**Actors and intended outcome:** An operator investigates a synthetic request, sees its structured log record, and follows it to the corresponding synthetic background operation. Developers can observe bounded service health and latency measurements without inspecting customer or financial records.

**Scope and non-goals:** The proposed first instrumentation slice covers one already-supported synthetic HTTP-to-job/consumer path, if a safe path can be identified. It adds correlation and tracing at the composition/adapter boundaries. A separate later slice may add OTel metrics and alert rules. A mock-generation pilot may be considered independently for one test interface. Production deployment, real user data, real funds, mounted Identity routes, live provider calls, audit-system changes, and production readiness are out of scope.

**Functional and non-functional requirements:** Preserve the health-only route inventory and loopback-only private listener. Keep domain packages independent from concrete log and telemetry SDKs. Generate a local request identifier at trusted ingress. Treat public `traceparent` as untrusted unless a separately reviewed trusted-proxy policy is adopted. Do not accept or emit baggage in the initial slice. Do not inject trace context into Mailgun or another external provider. The telemetry path must fail closed with respect to data minimization and must not block or change business outcomes when the collector is unavailable. Define startup, flush and shutdown deadlines before implementation.

## G3 — Technical design and security review

**Alternatives considered:**

1. Continue with `slog` only and add correlation IDs. This is the smallest path, but it cannot represent cross-process timing, parent/child spans or trace-to-span navigation.
2. Adopt OTel traces and metrics with JSON logs on stdout. This keeps signal APIs portable, supports Collector routing and avoids direct application coupling to a chosen vendor. It adds SDK, exporter, configuration, sampling, and collector operations.
3. Adopt separate vendor SDKs and clients, such as Zap, `client_golang`, and Jaeger-specific trace code. This gives direct backend integration, but duplicates instrumentation and makes later backend changes more costly.
4. Keep telemetry local and disabled outside tests. This avoids an exporter boundary, but does not meet operator trace lookup without a configured collection backend.

**Candidate direction:** Retain JSON `slog` and add OTel trace/metric SDKs at the application composition root. Use OTLP as the export protocol. Consider `otelhttp` for server spans after explicitly selecting an ingress-propagation policy. Keep domain and use-case packages unaware of exporters and vendors. The first lab can use an OTel Collector and Jaeger v2 for traces. Metric routing to Prometheus may be a separate slice, since the current contract does not define metric names, SLOs or alert thresholds. Emit JSON logs to stdout for the platform log agent. Configure each process once in its command/composition root. Do not add redundant HTTP client, pgx, SQL or provider auto-instrumentation until its attributes and overhead have been reviewed.

**Owner-selected direction:** On 2026-11-27, the owner selected Option B for detailed design. This records a direction only; no schema change, implementation or runtime activation is authorized.

**Option B detailed design candidate — pending technical review:**

| Concern | Proposed contract |
|---|---|
| Stored field | Add nullable `traceparent` to `identity.email_proof_deliveries`. Store only W3C Trace Context `traceparent`; do not store `tracestate`, baggage, request IDs, or span attributes in this field. Bound the value to the supported version-00 representation (55 ASCII characters) and reject control characters. The OTel propagator must parse and validate it before extraction. |
| Migration | Candidate next Identity migration is `000036`, subject to rechecking the live migration inventory before implementation. Add the nullable column and a bounded-format/length constraint. Do not add an index; the field is read with the existing claimed outbox row. Verify migration rollback/recovery rules and capability-version inventory before coding. |
| Producer | At trusted HTTP ingress, ignore caller-supplied `traceparent`, `tracestate`, and baggage by default; create a local trace root. When issuing the proof delivery, inject only that local span context into `traceparent` and write it atomically with the challenge and encrypted delivery row. If no valid recording or non-recording span context exists, persist NULL. Preserve the current outward HTTP response. |
| Consumer | Read the stored value when claiming the delivery. Validate and extract only the W3C Trace Context parent, then create a new span for each delivery attempt. Retries retain the trace ID but have distinct attempt span IDs. Invalid, absent, or unsupported context must not prevent delivery: start a new root and record a bounded status such as `missing`, `invalid`, or `extracted`. If batch processing is introduced later, use span links instead of choosing one job as the parent. |
| Database authority | The verifier runtime may insert the new column via an explicit column-level INSERT grant. The delivery runtime already has table SELECT for claiming rows, so it can read the field. Do not grant delivery runtime UPDATE on `traceparent`; its finalization query must not change it. Review the effective grants after migrations, including inherited and owner privileges. |
| Retention and deletion | Retain the field for the outbox row's existing lifecycle, including retry and terminal status, to avoid adding a terminal-path write permission. Extend the existing bounded SECURITY DEFINER expiry purge to clear `traceparent` when it clears the encrypted token and sets `purged_at`. Add an invariant that a purged row has no `traceparent`. Review function ownership, grants, batch limit, lease fencing and recovery behavior. The maintenance function is currently documented as unscheduled/undeployed; no production deletion guarantee exists until separately deployed and verified. |
| Provider boundary | Do not inject trace headers, baggage or context into Mailgun or another third-party provider request. Instrument the local provider call as a span, but keep the external request free of trace propagation. Do not record recipient address, proof token, provider response body or raw error in span/log attributes. |
| Logs and metrics | Derive `trace_id` and `span_id` from the active valid span context at the shared logging boundary, including a valid context when the span is sampled out. Keep `ChallengeID` as the existing bounded internal job correlation key where needed. Never use trace, span, challenge, request, user or tenant IDs as metric labels. |
| Failure behavior | Telemetry parsing, SDK, exporter, collector and backend failures must not change proof issuance, outbox commit, retry schedule or delivery result. Bound exporter queues, timeouts and shutdown flush; define these limits in the accepted implementation design. Durable audit remains independent of trace sampling and export. |

The synthetic verification must exercise the same HTTP-to-outbox-to-worker path. Required cases include: a local root despite hostile inbound headers; atomic context persistence; role-grant denial for delivery-runtime traceparent updates; valid/missing/malformed stored values; first attempt and retries; terminal and expired/purged rows; purge/recovery behavior; no provider propagation; sampled and unsampled log correlation; exporter outage; and sentinel leak scans of captured JSON and OTLP output. Tests must run against disposable PostgreSQL and a local provider/OTLP mock only.

The current schema places the encrypted proof in `email_proof_deliveries`. The verifier runtime has a column-specific INSERT grant; the delivery runtime has SELECT and column-specific UPDATE privileges. The existing bounded expiry function clears the encrypted token after challenge expiry plus 24 hours when no active lease exists. The exact migration and grant definitions must be re-read against the implementation base before coding.

**Alternative retained for comparison:** Option A correlates separate producer and consumer traces with an opaque internal `job_id`, without a schema migration. Operators would need to search by that job identifier instead of following one trace. The owner selected Option B, so Option A is no longer the selected design direction.

OTel messaging conventions support message-creation context as parent for single-message processing and span links for batch processing. ([Messaging span conventions](https://opentelemetry.io/docs/specs/semconv/messaging/messaging-spans/))

Use `request_id` for request lookup, `trace_id` and `span_id` from a valid span context, and an opaque `job_id` for a logical delayed job where needed. `slog` should receive trace fields through one handler boundary so caller-owned contextual attributes, `WithAttrs` and `WithGroup` remain correct. Metric labels should be low-cardinality values such as route template, method, bounded operation and result class. Never put request/trace/job IDs, identities, raw paths, SQL text or money amounts in metric labels.

**Ownership and trust boundaries:** Platform owns telemetry configuration and the common composition wiring. HTTP and worker adapters own span boundaries around external I/O and job lifecycle. Capability code may pass `context.Context` and approved low-cardinality events but must not import exporter or backend packages. The designated audit owner retains actor/action/target evidence in its access-controlled durable store. Telemetry is diagnostic and may be sampled or lost.

Public ingress accepts arbitrary client headers. The candidate generates its own trace root at the public HTTP boundary and does not adopt external `traceparent` fields by default. If a future deployment terminates TLS at a proxy, proxy trust and propagation need separate acceptance. Do not accept baggage in the first slice. Keep outbound propagation disabled to external providers. A future trusted internal service or queue may carry W3C trace context in a bounded, validated job envelope. That envelope design must account for retries, batch links, replay, payload size and untrusted queue data.

**Flow and contracts:**

```text
Public HTTP handler
  ├── generate request_id and local trace
  ├── emit structured log with trace_id/span_id when sampled
  └── selected synthetic job producer
        └── job context (explicit approved propagation)
              └── selected synthetic consumer and retry
                    ├── structured logs
                    └── OTLP trace → Collector → trace backend

Service metrics → OTLP → Collector → Prometheus (separate proposed slice)
JSON stdout → platform log agent → selected log backend
```

The synthetic path is identified in `TestIdentityZBrowserVerificationE2E` and `TestIdentityMailgunMockPipeline`, and the owner-selected Option B request-to-consumer design is proposed above, pending technical review. The E2E test uses handlers on a test-only TLS mux and a loopback provider mock. It does not change the production router, enable live email, or prove that the worker can query a production trace backend. Do not activate those routes or use a live provider as part of the observability pilot.

**Consistency and failure model:** Export is best-effort diagnostic work, with bounded buffers and timeouts. Collector or backend outage must not roll back or delay a committed business operation past its request deadline. Shutdown uses a bounded provider flush and then stops. Sampling does not affect audit durability or application results. Tail sampling, persistent Collector queue, automatic database instrumentation and trace-based security decisions are excluded until explicitly reviewed. A retry is a new processing attempt with a link or parent relationship chosen from the actual job semantics. A trace ID alone does not prove one-time processing, commit, delivery or audit completeness.

**Security and privacy:** Source-side allowlisting is the primary control. Exclude passwords, proof tokens, session/access tokens, cookies, Authorization values, email/contact data, raw DSNs, SQL query text/parameters, full provider errors, account IDs, customer/tenant IDs and transaction amounts. Do not assume Collector redaction can correct data that is already exposed at the application boundary. Use synthetic sentinels and inspect both JSON and exported OTLP payloads. Do not use user or resource identifiers as metric labels. Restrict Collector and backend ingress to the private network, use authenticated TLS for remote export when enabled, and decide retention, access control and deletion policy before any real Identity or Ledger telemetry leaves the service.

**Compatibility, observability and rollout:** Keep telemetry export disabled unless endpoint and credentials are explicitly configured. Never configure a production endpoint by default. Do not add a public scrape route. Start with local disposable lab services. Check host, port and receiver reachability restrictions. A candidate migration is described for review only; no migration is implemented. No production rollout is approved. A later deployment design must set sampling, retention, redaction, budgets, access policy, alert ownership and rollback.

**Decision status:** Option B direction selected by the owner; detailed G3 design remains proposed and pending technical review. Before implementation, resolve: (1) migration and capability-version inventory; (2) least-privilege grants and effective privilege review; (3) retention, purge scheduling and recovery; (4) public trace-parent policy; (5) telemetry endpoints, credentials and network boundary; (6) log/trace retention and access; and (7) exact AC and verification scope. Metrics and mock generation remain independent decisions. No code, dependency addition, runtime wiring, route activation, merge or production activation is authorized by this document.
