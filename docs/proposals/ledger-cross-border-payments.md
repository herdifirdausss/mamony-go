## G3 — Candidate architecture summary (not accepted)

Retain Go modular monolith, one PostgreSQL database, per-capability schemas, explicit facades and grants. Ledger owns accounts/journals/entries/balance and posting transaction; it has no dependency on other capabilities. Accounts owns tenant/owner mappings; Identity owns subject/credential/approval authority; Payments/Payouts own workflow and immutable intent/hold obligations; FX owns rates/quotes/position; provider owns external operation/evidence; reconciliation owns cases, not balances; settlement/accounting own batch/report/close. Treasury capacity ownership is a decision, not a new package requirement. Outbox relay and consumers use explicit contracts, not unrestricted DB access. No public arbitrary posting endpoint, Redis authoritative balance, message broker dependency, generic orchestration platform or independent service split required.

### Consistency boundaries to prove

| Boundary | Candidate local commit | Explicitly outside |
|---|---|---|
| Journal | scoped replay, journal/entries/account steps/balance, event, allowed participant effects | remote calls, provider state |
| FX group (after approval) | both currency journals, immutable group/quote, fees/position and approved capacity participation | wholesale FX settlement, external cash |
| Payout admission | exact intent authority/receipt, customer hold, usage and applicable funding reservation, operation identity | actual provider send |
| Dispatch claim | current admission fence, stable provider ref and potential-send state | remote result; stale worker cannot be fenced by DB lease alone |
| Evidence application | normalized semantic fact, guarded transition, required posting/participant effects or durable unresolved recovery | bank/counterparty true state beyond evidence |
| Matching / correction | guarded allocations and case transitions; approved exact command via ledger owner | arbitrary automatic journal or fictitious cash |
| Close | effective-date fence and pinned manifest; finalize only after validated checks | future adverse events, statutory restatement |

Local atomic cross-capability writes require explicit grant and tested narrow interface; no assumption all owners share transaction merely because database is shared. Unresolved authority/participant protocol blocks the affected action. Stage H must choose concrete boundaries, lock classes and interface, without coding.

### Cross-stage invariants

- Every journal balances within one book/currency; amount positive exact int64 minor units, bounded exact intermediate math; no summing across currencies.
- Every financial effect has authorized immutable economic identity; transport retries and events cannot create duplicate effects.
- Available balances, usage, position and cash reservations are different authorities; never double deduct a posted/reserved amount.
- Ledger history append-only for runtime. Corrections are authorized facts; stored balance drift is integrity incident, not an excuse for balancing plug.
- Unknown external outcomes retain applicable holds/usage and use original reference; no deadline/lease-based blind resend, fallback or release.
- Provider signature, accepted status, beneficiary credit, cash settlement and reconciliation are different facts. Missing evidence is not zero activity.
- Restore cannot undo an external debit; safe resume requires evidence, fencing, current authority and reconciliation.
- Profile A trusts its authoritative database/process. No independent compromise resistance, real compliance, external exactly-once or production SLO claim.

### Architecture review — concrete candidate (Stage H)

**Status: PROPOSED; G3 not accepted.** Review 2026-11-24. This section refines the candidate consistency boundaries above; it does not supersede an active contract. Reviewed actual main [architecture](../architecture.md), [conventions](../conventions.md), [PostgreSQL contract](../contracts/postgresql.md), [pool primitive](../../internal/platform/postgres/pool.go), [architecture checker](../../tools/archcheck/main.go), ADR-0001/0002 and ledger contract. Current pool checks login role and privileged membership, bounds connections, sets pg_catalog search path, offers WithTx/WithTenantTx and classifies commit as possibly unknown. It is not a financial coordinator or authorization authority. Current archcheck rejects direct cross-capability imports even of facades; adapters must be wired in app, and app cannot import private module internals. No ledger runtime present in reviewed baseline.

**H1 — Select hybrid Go plus narrow PostgreSQL mutation functions (FIN-C, DEC-02).** Alternative Go-orchestrated DML is simpler to debug and can satisfy transaction correctness under trusted runtime, but broad table mutation grants let an SQL-capable runtime bypass Go checks. A dedicated ledger engine adds cross-store atomicity/recovery and deployment costs before a demonstrated need. Recommend Go for pure domain validation, policy, workflow, canonical command construction, retry classification and interface orchestration; PostgreSQL for the authoritative mutation constraints, exact arithmetic, lock sequence, replay, account steps, balances and outbox. No provider call or business-rule DSL in PL/pgSQL. Use an independent oracle to check SQL/Go agreement; validate again in the write boundary rather than trusting a Go boolean/hash. If the restricted function design fails review or performance requirements, reconsider direct DML with explicitly accepted weaker role threat assumptions; do not silently downgrade.

Primary reference checks: [PG18 CREATE FUNCTION](https://www.postgresql.org/docs/18/sql-createfunction.html), [privileges](https://www.postgresql.org/docs/18/ddl-priv.html), [session/current user](https://www.postgresql.org/docs/18/functions-info.html), [SET ROLE](https://www.postgresql.org/docs/18/sql-set-role.html), [isolation](https://www.postgresql.org/docs/18/transaction-iso.html), [locking](https://www.postgresql.org/docs/18/explicit-locking.html) on 2026-11-24. Function owner privilege and caller identity differ; default PUBLIC execute requires explicit revocation; consistent lock order reduces, not eliminates, deadlocks. Pinned repository PostgreSQL 18.7 must prove actual behavior; documentation is not runtime evidence.

**H2 — Transaction composition without a global writer (FIN-C/D/E/F/H).** One PostgreSQL transaction belongs to one connection; two independent capability pools or independently committed facades cannot form one atomic transaction. Avoid generic shared transaction context, distributed transaction coordinator, arbitrary callback accepting pgx.Tx, and login roles with unrestricted DML across schemas. Use a named workflow transaction entry point only when atomic cross-owner effects are required. Example payout admission: payout runtime opens one transaction on its own role and calls a fixed payout-owned SQL entry point; that entry point invokes explicitly granted, owner-controlled narrow participant functions (Identity receipt/fence, policy usage, treasury capacity, ledger hold). Each participant validates its own durable state and writes only its own schema. Workflow function owner has only required EXECUTE and its own narrowly scoped write grants; ledger function owner writes ledger only. Go owns business orchestration and inputs; fixed SQL choreography owns only the indivisible commit path. Ordinary facade calls outside the path use separate transactions and explicit durable recovery, never an implicit shared transaction. No generic stored procedure engine or cross-schema unrestricted query.

Mandatory coupled effects must be unskippable by the entry point's runtime principal. Simply grant a payout runtime individual receipt-consume, reserve and post functions and expect Go to call all three is insufficient against an SQL-capable caller. Grant runtime EXECUTE only on the complete workflow wrapper; internal participant entry points restricted to specifically named no-login workflow execution roles, not directly to runtime. Where a primitive can be called independently, its standalone operation must itself be safe and authorized; never expose generic posting/approval-consume on a role that can bypass the workflow. Ledger internal primitive accepts registered operation/template and authoritative validated participant evidence, not arbitrary lines from untrusted runtime. No dynamic SQL/role delegation. No broad app coordinator credential. If an owning capability cannot expose safe narrow participation, keep action disabled until accepted design or choose durable staged protocol with explicit invariant and recovery; no claim of atomicity across connections. Ledger has no dependency on other modules: wrapper calls ledger; ledger does not invoke payment/FX/Identity internals. Cross-owner transaction contract is explicit in SQL grants and app wiring; no cyclic module dependencies.

**H3 — Role and caller model (FIN-C/D, DEC-05/14/16/18).** Names illustrative, not migrations. Schema owner/migrator non-runtime; prefer no-login function execution roles with only needed table/column privileges rather than broad ownership for each write path; separate read-only verifier and limited relay (outbox progress only) when needed. Distinguish dedicated capability login from definer owner. Outer entry checks authenticated login (session_user under restricted login and no session-authorization switching), template/capability allowlist and current durable authority; SECURITY DEFINER current_user is function owner, not original login. Nested function authorization uses exact EXECUTE grants to the specific no-login calling role and checks allowed original login/operation; do not rely on a caller-supplied role string, GUC, or assuming current_user inside callee identifies immediate caller. Prohibit unsafe SET ROLE/membership paths and direct runtime EXECUTE of private functions. Tenant GUC only context after trusted authorization; with platform-owned ledger, enforce scoped owner mapping/template and result access at facade/DB boundary, not RLS alone. No default PUBLIC execute; revoke in same migration transaction, default privileges reviewed, safe fixed search_path pg_catalog and trusted schemas with pg_temp last, fully qualify tables/functions, no untrusted CREATE, unsafe dynamic SQL or unrestricted function arguments. No broad read views that bypass forced RLS. Check effective privileges through catalog and real connections. Shared monolith process still trusted Profile A; credentials/SQL boundaries reduce accidental and scoped-role bypass, do not isolate complete process or privileged DB compromise.

| Proposed principal | Permitted operation | Explicitly denied |
|---|---|---|
| ledger runtime | approved standalone ledger command/query facade only as designed | direct journal/entry/balance DML, arbitrary raw posting, schema DDL |
| payout/FX runtime | named workflow wrapper, scoped own reads as approved | individual coupled participant calls, direct ledger/Identity/policy DML, other workflow wrapper |
| payout/FX workflow execution role (NOLOGIN) | narrow own writes and exact participant EXECUTE | runtime login, unrestricted ledger table DML, broad grant/role admin |
| ledger mutation execution role (NOLOGIN) | ledger tables and registered constraints only | cross-owner DML, login, grant admin |
| verifier / relay | restricted read / approved outbox progression respectively | ledger history or balance edits, customer admission, cross-tenant arbitrary read |
| migration/owner | approved offline migration and role/schema administration | use as application runtime, handler or worker credential |

**H4 — Explicit lock protocol (FIN-C/D/E/F/H/K).** Choose READ COMMITTED for bounded known rows, not as a universal predicate invariant. Candidate global class order: (1) operation/replay claim; (2) accounting period fence if applicable; (3) authority/ownership/freeze guard; (4) intent/approval/quote and operation-specific obligation guards; (5) limit/position/liquidity/refund capacity guards; (6) ledger account rows. Every class has stable total key order, including distinct guard types and book/account identity; derive complete lock set before mutations, lock union of affected accounts for FX group. Every conflicting path follows same order, including close/freeze, reversal, expiry/release, rescreen, dispatch, account open/close and reconciliation allocation. No arbitrary participant acquiring earlier-class lock after ledger accounts; if discovered new dependency, abort/replan before mutation; don't hold long DB locks during external I/O. Key claim first for replay, committed result must still be authorized before returned; never return sensitive result just because key exists. Within same class use explicit deterministic sorted keys/lock SQL with tested acquisition order, no unordered query assumption. For account close use same authority/obligation/account locks; no post-lock unchecked external close check. Period close uses same period fence if effective-date writers exist; no unnecessary global period-exclusive lock for all postings (shared admission vs exclusive close candidate, measure contention). Known row guards or uniqueness/exclusion constraints protect absence/predicate cases; Serializable only for specific paths if needed and tested. Document implicit FK/index/constraint/DDL locks and actual wait graph in Stage J; no deadlock-free claim. Handle bounded known 40001/40P01 abort by whole-operation retry; uncertain commit resolve same durable key; never reissue remote action on SQL failure. Test freeze-to-dispatch fence order separately; a local guard cannot cancel a remote accepted operation.

**H5 — Identity and replay (FIN-C/D).** Preserve LGR-03 uniqueness (authenticated capability, key) until accepted amendment; do not quietly widen uniqueness to tenant/currency/kind. Derive versioned namespaced *internal* financial key from immutable operation/economic fact in owning capability, not raw public Idempotency-Key; public idempotency scope owned by HTTP workflow. Canonical financial content includes book, account IDs, directions/amounts, currency version, operation/template, immutable intent/evidence and approved participant bindings; exclude trace/delivery metadata and volatile receipt presentation. Define order as semantic or canonical sort explicitly; prefer ordered journal positions, replay identical manifest. Store canonical content or sufficient typed durable fields plus computed fingerprint; DB computes/validates canonical representation under same documented encoding, never accepts unverified caller-supplied digest as proof. Separate semantic economic fact uniqueness from transport key (two keys cannot post the same fact twice). Existing committed key + equal content -> authorized same result; changed content -> conflict; denied new command -> no committed effect. PostgreSQL ON CONFLICT DO NOTHING may wait for another transaction whose row is not in original snapshot: use following statement at READ COMMITTED for committed replay lookup (tested against actual function execution and snapshots, not a single CTE assumption). No DELETE/expiry of posted key. Unknown commit repeat same identity; replay doesn't consume approval again or dispatch. Finalize exact fields, key encoding, SQL shape and error contract in Stage J.

**H6 — Atomic multi-currency group (FIN-F).** Keep single journal as first ledger gate. Candidate later group wrapper applies a bounded ordered manifest of independently balanced single-book/single-currency journals with unique stable child identities; no child can independently post as new work. Group claims parent identity before union lock set, validates each journal, all applicable account floors at deterministic journal boundaries (no netting a transient invalid per-journal state without approved semantics), int64 bounds and allowed participant effects. Assign one account sequence per affected account per journal, store both child IDs and all child outbox rows in same commit; consumer must not infer group is complete solely from receiving one child event; use durable group manifest or explicitly versioned group-aware event if needed. All-or-none local quote/fee/position consumption via complete wrapper. Do not put partner funding transfer or external exchange in same SQL transaction; external rebalancing uses durable independent legs and inquiry. No partial internal group committed state; FX-05/06 sequential contract needs explicit change before implementation. Reversal of group must be separately authorized with all current floors and linked original group; no generic inverse after external payout.

**H7 — Package and schema boundary.** Initial ledger slice only adds needed module.go, private domain/usecase/repository/postgres under internal/modules/ledger, and forward-only db/migrations/ledger when approved. App composition binds consumer-owned ports to other public facades, with narrow named transaction operations; no direct capability-to-capability import (archcheck prohibits). No generic transaction coordinator package, public database driver types in usecase/domain, empty placeholder folders, Redis balance cache, or broker before need. SQL objects stay owned/versioned in respective capability schema, migrations grant only explicit reviewed cross-schema interfaces. Pure domain amount types local until genuinely shared infrastructure needed; no shared financial domain grab bag. SQL functions are versioned migration objects, tested via real runtime roles; breaking function signatures use expand/contract or approved disabled migration window, never edit applied files. Exact table constraints and migration order Stage J; do not create roles now.

**H8 — Review tests and unresolved choices.** Abstract class-order model checked six illustrative operation traces (post, freeze, close, payout, FX, refund), zero violations of specified explicit order; this is not database/concurrent lock evidence and excludes implicit lock paths. No postgres/psql/initdb/container runtime available in local execution environment; Go binary present but no financial code to test. Required actual tests: runtime direct DML and PUBLIC/function search-path spoof, role/membership and nested invocation denial, wrong capability/template/tenant, unauthorized independent participant call, wrapper fault at each participant including outbox, two-session same key and balance/freeze/close/capacity races, reversal and group child replay, committed-but-lost response, period fence, bounded contention/deadlock and snapshot reads. Record exact migrations, actual login credentials (no secrets), SQLSTATEs, statements, assertions and CI results. No Go/DB/CI performance claims. Keep initial workload/limits and RPO/RTO open DEC-12.

Recommended design choices H1–H7 are candidates for explicit technical review, not approved ADRs. Stage I should propose focused edits to LGR, FX, PostgreSQL, IAM/PAY/OUT and ADR-0002 without altering active contracts until owner and reviewer acceptance; Stage J must resolve actual participant signatures, exact role grants, lock graph, canonical fields and tests. First ledger slice does not require building future payout/FX wrappers or risk modules, but must not expose unrestricted raw posting as a shortcut. Identity-first and platform gate remain in force.
