## G3 — Candidate architecture summary (not accepted)

Retain Go modular monolith, one PostgreSQL instance, autonomous capability schemas, explicit facades and grants. Each independent owner commits locally; Go workflow coordinates across owners. Ledger owns accounts/journals/entries/balance and posting transaction; it has no dependency on other capabilities. Accounts owns tenant/owner mappings; Identity owns subject/credential/approval authority; Payments/Payouts own workflow and immutable intent/hold obligations; FX owns rates/quotes/position; provider owns external operation/evidence; reconciliation owns cases, not balances; settlement/accounting own batch/report/close. Treasury capacity ownership is a decision, not a new package requirement. Outbox relay and consumers use explicit contracts, not unrestricted DB access. No public arbitrary posting endpoint, Redis authoritative balance, message broker dependency, generic orchestration platform or independent service split required.

### Consistency boundaries to prove

| Boundary | Candidate local commit | Explicitly outside |
|---|---|---|
| Journal | ledger-owned replay, journal/entries/account steps/balance, event and local guards | other owners and remote calls |
| FX group (after approval) | both currency journals, immutable group and ledger quote-use marker | FX/fee quote-owner and position finalization, external cash and settlement |
| Payout admission | each owner independently commits exact approval, cap, hold or funding reservation; payout commits progress/ready manifest | other owners and actual provider send |
| Dispatch claim | provider-owned claim vs no-send fence, stable provider reference, potential-send state and applicable local permit fence | remote result; stale worker cannot be fenced by DB lease alone |
| Evidence application | each owner commits semantic fact or local effect and durable result; workflow records confirmed progress or unresolved recovery | other owners and bank/counterparty true state beyond evidence |
| Matching / correction | recon-owned allocation and case transition; ledger commits exact correction separately | arbitrary automatic journal or fictitious cash |
| Close | ledger-owned effective-date fence and pinned manifest; Accounting confirms checks through durable protocol | cross-owner atomic close, future adverse events, statutory restatement |

Cross-owner ACID is an explicit exceptional design, not default. No shared transaction handle or direct schema access across autonomous owners. Unresolved authorization, quote/reservation and compensation protocols block affected action. See revised H below.

### Cross-stage invariants

- Every journal balances within one book/currency; amount positive exact int64 minor units, bounded exact intermediate math; no summing across currencies.
- Every financial effect has authorized immutable economic identity; transport retries and events cannot create duplicate effects.
- Available balances, usage, position and cash reservations are different authorities; never double deduct a posted/reserved amount.
- Ledger history append-only for runtime. Corrections are authorized facts; stored balance drift is integrity incident, not an excuse for balancing plug.
- Unknown external outcomes retain applicable holds/usage and use original reference; no deadline/lease-based blind resend, fallback or release.
- Provider signature, accepted status, beneficiary credit, cash settlement and reconciliation are different facts. Missing evidence is not zero activity.
- Restore cannot undo an external debit; safe resume requires evidence, fencing, current authority and reconciliation.
- Profile A trusts its authoritative database/process. No independent compromise resistance, real compliance, external exactly-once or production SLO claim.

#### H1 — Data ownership and extraction rules

One physical PostgreSQL instance; private logical schema and restricted runtime credential for each independent authority, no direct cross-owner DML/joins/FKs, shared pgx transaction handle or cross-schema SQL choreography as normal business integration. Cross-owner references are opaque IDs with lifecycle/version contracts and durable reconciliation. No read of another owner's live tables even just because same instance; query its authorized facade or an owned read projection (projection cannot grant spend). Cross-owner migrations must not require other owners' private schema shape. Use current archcheck: all cross-module calls through consumer-owned Go ports and app composition, no direct imports between capabilities, no private package access from app. Repository owns local transaction; never hold it open during another owner call, even in-process. No generic Saga framework, broker, service mesh, gRPC or 2PC required initially; a durable workflow in the owning capability, local jobs/outbox and typed adapters suffice. Separate deployment later needs new threat, service auth, transport contracts, timeout and migration review. Cross-owner ACID is an exceptional architecture choice requiring explicit ADR, extraction trade-off and approved scope; if an invariant truly needs one atomic boundary, prefer colocating its authoritative state in a single consistency owner over pretending independent stores are atomic. Retain Identity-first roadmap.

| Authority | Strong local invariant | Interaction outside transaction |
|---|---|---|
| Ledger | one currency journal; account lifecycle/floors; immutable replay, hold and capture/release exclusivity, atomic FX group, unique financial fact, ledger outbox; effective-date admission fence when accounting introduced | authorized typed commands, durable result and query |
| Identity | authenticated subject and current credential/role generation, exact approval/permit issuance once, revocation and issuance deny | approval/permit and revocation protocol, not direct ledger mutation |
| Accounts | owner mapping and eligibility status; ledger owns actual monetary account status/close fence | mapping lifecycle and authoritative restriction propagation |
| Policy | atomic cap check + reservation, consumed/released exclusivity, immutable rule version | reserve/confirm/release result |
| Fees/FX | pricing rule, immutable quote and exclusive claim for exactly one operation; position reservation | immutable execution authorization and ledger result confirmation |
| Treasury | eligible cash budget, exact reserved/used capacity, cash fact dedup | reserve, confirm/release with evidence |
| Payout/Payment | immutable intent, step identities/progress, one operation attempt, local transition/outbox | orchestrate independent owner commands |
| Provider | dispatch claim vs permanent no-send fence, original provider reference, normalized evidence | network call outside transaction, inquiry |
| Reconciliation/Accounting | case and allocation, report projection and close manifest | correction commands to ledger, ledger period fence API |

Financial account mappings may be separate from ledger but spendable amount and actual posting/freeze/close constraint must be enforced by ledger's own authority. If a hard cap depends atomically on a ledger balance rather than an independent conservative reservation, place that particular guard in ledger. Do not require a module boundary for every rule. Treasury can remain a logical capability until first approved funding slice. Candidate future deployment clusters (not committed): Identity; core financial ledger including posting groups; payments/provider orchestration; risk/compliance; operations/reporting. Split only after measuring need and evaluating cross-boundary safety.

#### H2 — Local monetary transaction and mutation authority

Owner selected **Option A — Go repository with direct parameterized SQL** on 2026-11-24, superseding the earlier recommendation of restricted SQL functions. Maintainability rationale: keep financial rules in Go domain, usecase authorization/orchestration in Go and transaction/locking/replay/persistence in owned repository; query-only changes can ship with the binary if schema compatible. Use PostgreSQL declarative constraints, explicit stable row locks, unique keys and grants. READ COMMITTED candidate for known rows; test predicate/absence guards or justified Serializable as required. Ledger local order: replay/economic fact claim, owned status/period/obligation guards, sorted accounts; no global lock graph or foreign calls inside tx. Ledger writer role needs scoped INSERT and UPDATE of owned balance/sequence/status columns and SELECT as required, never schema ownership or broad grants. Deny runtime UPDATE/DELETE/TRUNCATE of immutable history and other roles' ledger mutation; no cross-owner DML. Check privileges required by actual lock queries, no blanket grants. A malicious or erroneous Ledger writer may bypass Go aggregate/template/floor checks where declarative constraints cannot enforce them; verifier detects discrepancies but does not prevent writer abuse or all economically wrong balanced postings. Profile A trusts the Ledger process and scoped writer. Owner chose implementation approach, independent technical reviewer must explicitly accept residual risk before affected slice. No customer/public posting, no arbitrary caller-selected accounts, no GUC-as-auth; actual service caller derived by facade under trusted composition. No mandatory PL/pgSQL, dedicated engine or shared SQL choreography. Stored functions/triggers for procedural financial rules only after separate justified decision (measured need or stronger threat boundary); do not silently reintroduce Option B. Future service extraction requires network caller auth/currentness review. No full-process or DB-owner compromise resistance claimed.

Single journal commit includes journal/entries/account steps/balance, unique financial fact, replay and event. Hold and release/capture transitions use local hold ID and exact original binding; no negative floor, no duplicate capture or release, no cross-owner call inside transaction. Internal FX commits bounded two-journal manifest, both currency journals and child events, per-account sequences, group replay, exact quote execution identity and local ledger-side consumption marker; lock union of accounts. External quote/position owner finalizes its own reserved state separately. Group must reject independent child posting, verify all required floors at each approved journal boundary and never claim external PvP. Ledger returns committed group IDs; consumer receiving one child must not infer full workflow completion. Keep single-journal gate first, no group code before explicit FX contract amendment.

#### H3 — Durable orchestration and command contracts

Payout/Payments/FX use their own Go use case as orchestrator, not app composition or a generic coordinator service. For each step persist intended command + immutable payload binding and stable command ID in workflow's local transaction *before* call. Invoke owner outside transaction; owner commits business effect, stable result and event atomically. Record response/progress with expected version in orchestrator transaction. Loss of response, timeout or crash between any two commits -> inquire/replay identical command ID and content through owner; do not issue new identity. Distinguish known refusal/no effect, committed success, unknown outcome and retryable no-effect abort. A synchronous in-process call has same failure semantics as future remote transport. Use bounded retries and durable retry time, worker leases for local progress only, no assumption lease prevents old execution. Consumer inbox and effect/progress commit together where needed. Owner command replay scoped to authenticated capability, key (LGR-03 retained), exact canonical financial content; distinct semantic economic fact uniqueness and authorized result read. Public request idempotency and internal operation/step IDs are different identities. Preserve command receipts and terminal tombstones through retries/restore and relevant horizons. No random new keys on retries.

Suggested command shape (illustrative, not Go interfaces yet): Reserve/Query/Resolve by operation ID, intent digest/version, exact amount/currency, authority binding and stable step ID. Each result names owner, resource, generation, status, exact binding, effect IDs and evidence. No raw DB transaction in facade. Persist terminal canceled/no-effect tombstone for operation even when reserve never arrived, so delayed Reserve cannot resurrect capacity or hold. Same owner serializes reserve vs terminal cancel, and cannot change immutable content. Releasing a committed reservation uses separate stable compensation identity, references original receipt and proven no-send/nonexecution or approved definitive evidence. Expiry may schedule inquiry/review, but cannot silently free an operation that can still execute. Cases with no safe compensation remain restricted and visible. A business compensation is a new journal/transition, never deletion or rollback of another owner's commit.

#### H4 — Payout saga and irreversible boundary

One versioned immutable payout intent -> Identity approval bound to operation -> Policy reserve -> Ledger hold -> Treasury reserve if applicable -> durable READY manifest of exact committed prerequisites -> provider dispatch admission -> external inquiry/evidence -> ledger capture/clear/return and policy/treasury resolution -> terminal workflow only after required confirmations. Ordering of pre-send reservations is candidate; owner-specific cap/floor checks remain atomic. Optional FX requires explicit committed group and valid target funding, no implicit reversal after conversion. Never issue provider dispatch based on stale cached status or a missing receipt; require exact operation, beneficiary version, hold, usage, funding and authorization evidence. Provider owner has stable reference and one serialized transition between NOT_CLAIMED/NOT_SENT_FENCED and POTENTIALLY_SENT (claim is conservative irreversible point). Persist dispatch request before external I/O; claim can precede actual network send, and lost claim response is unknown. Once claim wins, timeout does not prove no-send. Duplicate worker uses original provider contract/reference; no blind resend or alternate provider. Cancellation closes provider admission using same serialized identity even if original request has not arrived yet; only after provider's durable NOT_SENT_FENCED proof may release pre-send resources. If claim won, preserve hold/usage/funding pending inquiry or definitive evidence. Payout cancellation is not terminal until every applicable participant is terminal or acknowledged not applicable. A late step or duplicate cancellation must not recreate resource. Real external debit/fulfillment/returns must be recognized under authorized service path even when customer is frozen. Don't release customer funds solely because a provider debited; rail-specific evidence and clearing policy govern finalization.

| Fault | Safe recovery |
|---|---|
| Policy reserved, response lost | query/replay same reserve; no second allocation |
| Ledger hold committed, orchestrator crashes | recover exact hold ID; no second hold, no dispatch until prerequisites confirmed |
| Treasury refuses | request provider no-send fence, resolve/release committed holds/caps, keep approval bound to original operation |
| Cancel before delayed hold or dispatch | terminal tombstone in each owner; provider no-send fence before release; retry old command must be refused or return old terminal result |
| Cancel races provider claim | provider fence/claim winner determines whether release is allowed; claim winner remains unresolved |
| Provider timeout after acceptance | same-reference inquiry; no new send/release until definitive evidence |
| Compensation fails / response lost | persist COMPENSATING or exception, replay exact compensation, do not report completed cancellation prematurely |
| External success but ledger result absent | recover posting same semantic fact, workflow remains processing, never charge/send again |

#### H5 — Security linearization is an explicit decision, not eventual authorization

Existing IAM-12/LGR-12/PAY-05/OUT-05 current authority requirements must not be weakened silently. A one-time approval is consumed by Identity **for exactly one immutable operation** (subject, tenant, action, resource, amount/currency, beneficiary version, generation and expiry); Identity's committed result is durable/replayable only for that operation. If downstream fails, do not make approval reusable for new intent; same operation may resume under approved validity policy. This changes all-or-none consumption semantics of initial H and requires owner acceptance. A preflight synchronous check followed by ledger or provider call has a TOCTOU race; an approval token, cache or asynchronous revocation event alone cannot guarantee immediate revocation. Candidate protocol: separate exact operation authorization from short-lived single-use dispatch/admission permit; Identity serializes permit issuance against revocation, stores permit and original operation binding; target owner enforces one effect/claim for permit, deadline, current local deny fence and durable identity. Freeze requested stops new permits immediately at issuing authority, then sends monotonic deny/fence commands to every enabled money admission/dispatch authority, which durably reject older epochs and acknowledge. Fence at target serializes with local hold/dispatch claim; a delayed older permit cannot start after target fence. Freeze remains PENDING until required target barrier acknowledged; return unresolved/in-flight operations, not a claim of no external effect. Permits/operations accepted before each target fence may already be in flight, including work claimed but not yet sent; cannot guarantee cancellation or zero external-send window. Do not permit unfreeze by stale event; monotonic epoch and independent approval. If downstream unavailable, fail closed for new required permit/authorization and leave freeze pending. Existing contracts require currentness; precise permitted in-flight semantics, target set, expiry/clock, issuer trust, transport integrity, revoke/consume race and recovery must be explicitly accepted under DEC-07/14/16/17 before enabling money. If owner requires zero-window revocation from Identity commit (not completion barrier), colocate relevant admission authority or adopt stronger coordinated protocol, or keep operation disabled.
