# ADR 0004 — Internal password-authentication foundation (Draft PR #39)

Status: **Candidate, unmounted; not a public login or session**.

## Context

Identity already supports pending registration (Argon2id v1 verifier), contact-bound email verification, and a strict browser-verification flow. Existing PostgreSQL credentials deliberately separate registration, email verification, and delivery; registration/verifier runtimes MUST NOT read the stored Argon2id digest. A password login is not implemented and an email proof alone does not confer a login session or authorization for financial operations.

The new password-check boundary must avoid differentiating a validly shaped *unknown* email from a known account based on whether Argon2id ran, and must refuse accounts without verified current contact or with non-ACTIVE status. It must not create a session cookie or token, or return credentials in HTTP error text.

## Decision

**Usecase:** `PasswordAuthentication.Authenticate(ctx, email, password)` is a non-HTTP, non-session primitive. It canonicalizes the email and applies the existing NFC verification normalization. It queries one server-owned credential record through `AuthenticationCredentialReader` and runs **exactly one bounded real Argon2id verification for any well-formed, present or absent alias**. The absent-record path uses a fixed, structurally valid, artificial v1 salt/digest; this verifier never represents a real identity and cannot yield an accepted subject, even if a fake test KDF reports a match. For present accounts, use only the DB-owned verifier, not password-specific client-supplied KDF parameters. A successful match returns an **internal subject candidate** ONLY when the current contact is verified and status is `ACTIVE`. This candidate is not proof of a live session, authorization, MFA, or a resource access grant.

All denied credentials (unknown alias, bad password, `UNVERIFIED`, `SUSPENDED`, `FROZEN`, `DELETED`, missing verified contact) use **`ErrPasswordAuthenticationDenied`** with no subject. Any PostgreSQL, KDF, corrupt parameter or cancellation failure uses **`ErrPasswordAuthenticationUnavailable`** without wrapping raw SQL, verifier content, or password. Malformed email/password is rejected before expensive work and has no account-existence implication. The usecase never logs or returns password or digest.

**Persistence:** Migration **v8** adds **no schema objects and no data rewrite**. It grants the new, separately provisioned `mamony_identity_authenticator_runtime` role column-scoped SELECT only to `subjects.subject_id/status`, `email_aliases.canonical_email/subject_id/verified_at`, and `password_verifiers.subject_id/kdf_version/memory_kib/iterations/parallelism/salt/digest`. It cannot read email challenges, encrypted delivery envelopes, HMAC admission keys, event outbox, migration history, or ungranted columns; it cannot update states or password verifiers, insert events, create tables, or assume migrator role. Existing registration and email verifier roles remain forbidden from reading password verifier material. Production provisioning of this role is separate: this PR adds a **synthetic fixture role only**. The SQL is forward-only and fingerprinted; historical migrations v1–v7 remain immutable.

**KDF:** Reuse the existing credential adapter `PasswordHasher.Verify`: Argon2id v1 only, 64 MiB, 3 iterations, p=1, 16-byte salt and 32-byte digest, with bounded concurrent slots and invalid-parameter rejection before expensive KDF work. The authenticator store independently validates the DB values before translating signed columns to unsigned domain parameters. Do not silently rehash on login; password rotation and future KDF version upgrade require an ADR.

## Out of scope, unresolved risks

- **No public login route**, session issuance, refresh/cookie persistence, session database, logout/revocation, step-up/MFA, user/tenant authorization, device binding, or token-to-subject mapping is implemented. No financial capability can trust the internal subject candidate directly.
- There is **no global or per-email login admission gate**, no adaptive abuse control, no public timing-envelope policy, and no throttled Argon2id workload approval. The dummy verifier reduces *KDF-presence* timing differences for validly shaped emails only; it does **not** ensure constant-time database lookups or eliminate all enumeration signals. Before any route is exposed, charge an account-independent, distributed, HMAC-keyed budget **before database lookups and KDF**, including unknown aliases; separate login and signup budgets and bound CPU/memory concurrency for a realistic deployment. Treat fixed-window burst/NAT constraints as explicit risks.
- Credential-stuffing detection, breached password handling, account lock policy, anomaly alerts and inaccessible-account recovery are open. Do not leak account-specific reason codes in future public login responses. A generic login denial is not a success indication for an inactive account.
- If verification is changed concurrently with checking status, any future session issuer MUST re-evaluate eligibility/credential state using an authoritative, race-safe decision. An isolated successful password check does **not** guarantee the account was never suspended after lookup. Secure session creation must be a separately atomic/conditional operation.
- Enforce legitimate use of internal subject candidates, sensitive memory/DB credential handling, and deployment-specific TLS/proxy policy; keep the chain Draft.

## Tests

Unit tests cover known/unknown aliases, correct and wrong password, unverified/suspended/frozen/deleted accounts, KDF on unknown aliases, impossible dummy-verifier activation, malformed inputs, cancellation, unknown SQL/KDF errors and failure redaction. Disposable PostgreSQL integration tests use a real Argon2id credential for a freshly registered pending subject, then actual email-proof activation before accepting its subject candidate; they reject unknown/wrong/inactive credentials and verify wrong-role DB denial. SQL privilege tests assert exact allowed SELECT columns and rejection of privilege escalation, writes, cross-role credential reads, security event access, challenge/admission/envelope reads, and migration history. The testgate mandates the named role and real DB tests. No CI result justifies mounting a public login.
