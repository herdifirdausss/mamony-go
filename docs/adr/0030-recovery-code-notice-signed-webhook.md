# ADR 0030 — Signed Mailgun reconciliation for recovery-code security notices (Identity v27)

Status: **PROPOSED / stacked Draft PR #67** based on Draft #66. Unmerged, unmounted and inactive by default. This is not an approval issuer, authentication factor or permission to activate public password recovery.

## Problem and decision

Identity v26 delivers two sensitive, **token-free** security alerts: `RECOVERY_CODES_ENROLLED` and `RECOVERY_CODES_ROTATED`. Mailgun HTTP 200 with a valid Message-ID means only provider **submission accepted**; it does not establish mailbox delivery. The already-reviewed v17 `PASSWORD_CHANGED` and v23 `PASSWORD_RECOVERED` signed webhook reconciliation cannot access or mutate this new purpose-specific queue. Identity v27 creates an independent Mailgun callback recorder and aggregate-only reconciliation without widening the v26 sender's or monitor's existing privileges.

**Cryptographic trust boundary:** A new unmounted `MailgunRecoveryCodeNoticeWebhook` delegates to the existing `MailgunSecurityNoticeWebhook` signature validator. That handler validates a bounded JSON body, timestamp freshness, Mailgun HMAC-SHA256 signature with constant-time equality, explicit signing-key rotation (one/two keys), expected Mailgun domain, event kind/severity and canonical Message-ID. It rejects forged signatures, unsupported event types, wrong domains, malformed token/timestamp or messages before invoking a SQL recorder. No route is mounted and no real provider webhook key is configured. Its separate PostgreSQL credential `mamony_identity_recovery_code_notice_webhook_runtime` has **only schema USAGE and EXECUTE on** `record_mailgun_recovery_code_notice_receipt(token_digest,event_digest,message_digest,delivery_state,event_at)`; `session_user` original login is checked inside SECURITY DEFINER. The handler passes only SHA-256 digests and normalized state/time—not signatures, raw token, message, email address, subject or provider body.

## Ordered state, callback-before-ACK and replay

The new `recovery_code_notice_mailgun_receipts` table is scoped to this purpose alone, with 32-byte token digest and event digest UNIQUE constraints (including parallel replay), 32-byte Message-ID digest, bounded provider event time, event state and recorded time. A duplicate signed callback acknowledges safely without creating a second receipt or downgrading a previously higher-severity state. Valid provider-reported outcomes include `TEMPORARY_FAILURE`, `DELIVERED`, `PERMANENT_FAILURE`, `COMPLAINED`, `UNSUBSCRIBED`; their rank is monotonic (a permanent bounce outranks delivered, complaint outranks bounce, unsubscribe outranks complaint). The original v26 sender **still alone** finalizes its 45-second leased Mailgun submit. v27 redefines that owner-controlled finalize in place, retaining its signature and role, and first looks for pre-existing provider receipts matching the exact accepted Message-ID digest. Thus callbacks arriving **before a Mailgun API ACK** reconcile when the ACK commits; later callbacks update only matching, accepted `password_recovery_code_notices`. An unknown valid provider receipt remains unmatched and is visible only as a count, never linked to an account by guesswork.

Retain v26's original five-column `recovery_code_security_notice_health()` contract, fixing `submitted_unconfirmed` to count only `SUBMITTED` or `TEMPORARY_FAILURE`, not delivered/bounce/complaint/unsubscribe. Add a second count-only `recovery_code_security_notice_delivery_health()` yielding `delivered`, `provider_failures`, `unmatched_events`. Existing accepted rows are conservatively backfilled to `SUBMITTED`—**never silently declared delivered**. Monitoring role stays read-only EXECUTE on only these aggregate functions, with no SELECT on the underlying receipt, users, emails or notification tables. Maintenance alone may delete at most 100 digests older than seven days per call; this does not delete the separate 7-day recipient erasure, immutable security audit, backup codes or recovery challenges.

## Verification contract

Real disposable PostgreSQL integration must exercise signed unmounted HTTP requests before/after the provider ACK, parallel webhook replays, monotonic delivered/bounce/complaint/unsubscribe ordering, unknown Message-ID, forged HMAC and wrong domain. Correlate only the actual v25 `RECOVERY_CODES_ENROLLED` / `RECOVERY_CODES_ROTATED` alerts sent via the v26 local Mailgun mock, not admin-minted stand-in jobs. SQL matrix must deny every direct table operation and cross-purpose EXECUTE for v27 webhook, including the v17 and v23 recorder functions; v26 sender and monitor must be unable to record v27 callbacks. The same signing and Mailgun HTTP app configuration must never be treated as a replacement for independent recovery-code enrollment authority.

### Remaining security gates

The new delivery state reflects **provider-reported** events rather than independently verified human inbox receipt. We still need delivery/bounce suppression and abuse routing, on-call thresholds, production webhook key custody and rotation, key management and provider setup, safe process supervision, secure customer-facing code display, independent AAL/MFA bootstrap approval issuer, lost-all-backup-codes policy, anti-enumeration HTTP, explicit human risk review and deployment approval. A compromised Mailgun signing credential can forge provider status; a privileged PostgreSQL owner can alter state. No live mail, public reset, real enrollment or webhook routing is enabled by this Draft PR.
