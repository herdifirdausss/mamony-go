# ADR-0042 — Proposed context-aware forward-only migration executor

**Status: PROPOSED DEC-01 AMENDMENT / OWNER-ACCEPTED DETAILED DESIGN CANDIDATE ONLY.** 2026-11-25; consolidated candidate 2026-11-26. ## Context

At main f6b9a2d1f46413e7c87db0cc09d13acc4261c438, the shared runner uses an outer native pgx session for target lock and verification and a separate golang-migrate driver session for execution. The pinned driver uses independent/background contexts for initialization, lock, version, and metadata operations; its SQL batch has a separate 45-second timeout. The CLI's 180-second caller deadline is not a proven end-to-end bound. Legacy dirty marker, body+fingerprint transaction, and clean marker are distinct transactions. Existing preflight checks the applied manifest prefix, not necessarily exact requested final version. Connection failure does not establish whether COMMIT occurred. See the active [runbook](../runbooks/platform-migrations.md).

## Proposed decision

Retain PostgreSQL 18.7, Go 1.27, native pgx/v5, immutable forward-only SQL files, existing fingerprint format, separate capability ownership and administrative-only invocation. Subject to separate authorization and actual compatibility evidence, replace golang-migrate execution with a minimal native pgx executor, not a general migration framework.

- A single dedicated session owns the fixed target lock throughout verification and mutation. No app pool, runtime auto-migrate, generic target selection or reconnect-to-resume.
- Explicit transaction per version includes the unchanged reviewed SQL file (body and existing trailer) and clean version metadata. Confirm expected prefix and next fingerprint before commit. Stop on cancellation before starting another version. Do not claim all versions commit together or all possible SQL effects are transactional.
- Preserve existing metadata schema and historical hashes/timestamps; reject legacy dirty or inconsistent history. Success requires the verified exact requested target, settled execution and resource cleanup, and confirmed durable terminal resolution. Distinguish cause, attempted-version effect, last verified durable prefix (including a proven fresh empty prefix), and resource cleanup; a confirmed commit remains committed even if the run cannot report success. Unresolved COMMIT or cleanup blocks further execution.
- Immutable bounded manifest snapshot, role/schema/database identity, and bounded work/cleanup/observation. No automatic retry, force, down, repair, engine fallback or metadata rewriting.
- Durable, exclusive admission and execution intent must be recorded before the first database mutation, including metadata bootstrap. Unresolved intent survives process death and prevents new execution until explicitly authorized settled reconciliation; fail closed if the admission authority is unavailable. Unknown outcomes require durable operational quarantine, not merely a record written after an error is returned. The bounded candidate uses one trusted administrative host and a preprovisioned persistent local journal outside the target database recovery boundary (DA-A). One global administrative gate serializes all managed migration, restore and reconciliation operations, followed by the existing target advisory lock. Logical slots survive incarnation changes. A trusted external provisioner binds each incarnation to approved resource and inventory evidence; restore requires a durable fence and explicit rebind. No new target registry or service. Exact storage, credential enforcement, inventory and durability feasibility remain open; an in-memory error is not a restart fence.

## Alternatives

A: retain golang-migrate and add strict final verification/graceful stop. Low implementation change but no direct in-flight caller context or atomic clean metadata.

B: context-aware driver adapter. Retains orchestration but split metadata and driver lifecycle remain complex.

C: native pgx per-version transaction (recommended candidate). More direct control and fewer session boundaries, but repository owns migration engine correctness, compatibility, fault evidence and cutover.

D: new framework or subprocess-only wrapper. Extra dependency/lifecycle cost; process termination is not proof of DB rollback.

## Consequences and gates

Legacy failed-body dirty metadata is existing tested behavior; proposed native confirmed rollback preserves the previous clean prefix. This is a behavioral contract change, not a refactor. Preserve legacy characterization and add distinct native acceptance rather than silently rewriting assertions. Neither history hashes nor locking protect against compromised administrators. Time-derived fields may differ because explicit transaction start differs from legacy batch; verify semantics with explicit oracles.

The current engine remains default until a separately accepted implementation and controlled cutover. Static integrity evidence covers 37 files at the historical reviewed corpus revision 76d417d35571b28b7aa748577861fc3a1f9e6dcb; it is not real engine equivalence. Fresh-state admission requires approved provisioning provenance and target identity, including restore/incarnation disposition, expected object inventory and owner/grants; absence of metadata alone cannot establish freshness. Require actual isolated old/new compatibility under H1–H7 (historical compatibility scenarios), including populated Identity v11→12, v26→27 and v34→35; no real Platform/Ledger next release upgrade claim. Use one shared monotonic work budget plus bounded cleanup and a separate additive mandatory fault-test group. Deadlines do not guarantee OS/storage or backend termination. DA-A assumes trusted single-host storage continuity and sole administrative authority, not silent storage rollback, host loss, HA or compromised administrators. If these assumptions cannot be demonstrated, stop and reevaluate DA-C (independent control store). Actual fault/CI feasibility and exact implementation scope remain blocking. No mixed writers, live migration, production cutover or activation. #105 remains open under #14 and is a prerequisite to Ledger runtime/production. Independent technical acceptance mandatory before production.

## Proposed DEC-01 amendment wording

Retain the accepted PostgreSQL/Go/pgx versions, per-schema roles, immutable forward-only SQL and canonical fingerprint verification. After separate accepted engine implementation and cutover gates, replace golang-migrate orchestration with a dedicated native pgx executor using context-aware per-version atomic SQL/fingerprint/clean-version transactions, bounded lifecycle and explicit durable outcome classification; preserve legacy dirty refusal and historical metadata. Require exclusive durable pre-mutation admission, restart-safe quarantine, externally verified identity and freshness, restore fencing and explicit reconciliation as specified in the [proposed PostgreSQL contract](../contracts/postgresql.md#proposed-native-migration-contract-not-effective). Cross-slot quarantine policy remains unresolved; do not infer permission to continue unrelated slots. This proposed wording does not supersede the current DEC-01 today.
