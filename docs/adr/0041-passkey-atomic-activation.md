# ADR-0041 — Proposed atomic possession verification of a staged passkey

**Status: OWNER-ACCEPTED BOUNDED SYNTHETIC DIRECTION / FINAL CANDIDATE REVIEW PENDING.** Related [Critical issue #78](https://github.com/herdifirdausss/mamony-go/issues/78) and [G0–G4 proposal](../proposals/identity-passkey-atomic-activation.md). Unmerged candidates #80/#81 exist; historical pre-acceptance implementation remains a lifecycle deviation to record, not retroactive independent acceptance.

Owner accepted D1–D4, bounded synthetic requirements and technical direction on 2026-11-25 ([owner decision record](https://github.com/herdifirdausss/mamony-go/issues/78#issuecomment-7150570178)). The existing three-minute challenge and ten-minute staging limit remain; no automatic cleanup or recovery release. Platform #14 owns recovery foundation; Identity #78 owns credential semantics and recovery obligations. Production delivery, recovery continuity and activation remain blocked. Under adopted main governance #89, independent technical acceptance is not accepted; it may be deferred only for an eligible, separately owner-authorized synthetic merge after candidate-specific containment, review and exact-head CI. Production readiness NOT ACCEPTED. No merge or production activation authorized.

## Context

V33 creates a globally unique `PENDING_ASSERTION` credential after original password-backed registration/nonce/admission. V34 binds a fresh three-minute assertion nonce to the same original live session, RP, subject epoch and pending credential, and provides a restricted read-only evidence reader. V35 uses a pinned maintained WebAuthn library to validate genuine `webauthn.get` signature and UP/UV/counter/BE/BS, but `VerifyOnly` is repeatable; the nonce is not consumed. Persisting `ACTIVE` based merely on signed assertion would mix technical possession proof with policy authority to log in or bootstrap independent recovery.

## Owner-accepted bounded synthetic direction (final technical review pending)

Use one **separately privileged, internally invoked SQL finish** as a trusted-Profile-A verifier oracle. It accepts only original server-owned v34 evidence paired with already signature-verified facts; it takes fixed locks subject+alias → original session → pending credential → exact challenge and rechecks DB-clock expiry, current ownership/epoch/contact, original v30/v32 consumed stage proofs, source COSE byte equality, RP, state, BE and counter freshness. Commit the one-use challenge consumption, transition `PENDING_ASSERTION → POSSESSION_VERIFIED`, current sign count and backup state, identifier-only event and mandatory contact-verified queued notice atomically. Any failure rolls back all. No caller-selected subject or arbitrary SQL role flag.

The existing v33 `PENDING_ASSERTION` CHECK must be enlarged by a **new, forward-only Identity SQL migration 000035**, retaining historical v33/v34 fingerprints. Capability is called v36 because v35 was Go-only signature verification. The independent activation-finisher role is EXECUTE-only, `session_user`-gated, and may not read/write tables or issue sessions, login grants or recovery approvals.

## Alternatives and trade-offs

- **Direct ACTIVE:** fewer states, but accidental entitlement escalation by future readers and no accepted login/assurance policy. Rejected for this bounded scope.
- **Nonce-only consume:** replay protection without explicit durable possession state or notification. Does not satisfy traceable credential lifecycle.
- **Application-side read then separate update:** vulnerable to TOCTOU, replay, lost audits and partial side effects. Rejected.
- **Proposed SQL one-transaction finish:** serializable authorization at Profile A root, but DB cannot independently verify WebAuthn signature; a compromised finisher credential can lie about signed facts, so it must never be treated as independent factor authority or stronger Profile B.

## Acceptance and negative tests

Require real signed WebAuthn assertion fixture coupled with real PostgreSQL tests for 16 concurrent finishes with one winner; replay, replaced nonce, another valid same-subject session, stale epoch/revoked session, changed RP/COSE, failed/stale counter, invalid BE/BS, expired challenge *after lock wait*, late duplicate event/notice rollback and clean corrected retry, role grants denial and original `session_user` provenance. Include no-mounted-route inventory, no login/session/recovery eligibility, and sanitized uncertain COMMIT tests.

## Release constraints

Remain strictly unmounted; `POSSESSION_VERIFIED` must NOT authorize password-independent account recovery, login, higher assurance or financial approval. The separate notification queue has no worker and `PENDING` is not evidence of delivery. Complete browser options, authorization, ingress/proxy, key custody, role isolation, device loss, backup/restore and alerting decisions before any public release.

**Decision owner approval:** ACCEPTED for bounded scope. **Independent technical acceptance:** NOT ACCEPTED. **Code/CI evidence:** candidate migration, bounded-role tests and synthetic PostgreSQL/WebAuthn tests exist in unmerged PR #81; see the exact-SHA CI ledger in [#78](https://github.com/herdifirdausss/mamony-go/issues/78), not a production deployment claim.

## Concurrency and code-review findings (2026-11-23)

The v34 issuer requires subject+alias → session → pending credential → challenge; the v34 evidence reader first acquires shared subject/alias and session locks, then performs a joined `FOR SHARE OF c,a` for credential and challenge. For the future finisher, acquire subject+alias and session **before** an exclusive credential lock and **then** challenge lock. Recheck the original v30 intent/v32 admission and actual server clock after conflicting row locks. Because joined locking and other writers can interact, add an explicit three-way **reader vs issuer vs finisher** real-PG deadlock regression; never infer lock acquisition order from SQL JOIN syntax. [PostgreSQL 18 explicit locking](https://www.postgresql.org/docs/18/explicit-locking.html).

The finisher must be given **the exact v35 evidence snapshot**, including byte-identical COSE public key and prior counter; it must not refetch a new key and treat an earlier signature as verification of it. The SQL role is a privileged verifier oracle only under Profile A. Even after a successful proof, `POSSESSION_VERIFIED` carries **zero** login, independently trusted recovery or financial permissions.

V34 can overwrite a consumed nonce row. Review whether the credential needs a non-secret `possession_challenge_id`/audit relation to preserve original challenge lineage after overwrite; storing the random nonce or any bearer in audit is out of scope.

The detailed proposed **28-case** acceptance/test matrix and schema/role changes reside in [the Critical proposal](../proposals/identity-passkey-atomic-activation.md#g4-supplement--executable-test-matrix-for-the-future-accepted-slice). **Only a subset is currently exercised** in synthetic PostgreSQL CI; replay, signed snapshot binding, role separation, rollback, and the preverified 16-claim DB race have runnable tests. The draft DB tests now include cross-subject ownership denial, epoch rollover, verified-alias change, superseded original intent, unconsumed original admission, rotated nonce bytes, session revocation, staging-age expiry, post-lock challenge expiry, and 16 SQL finishers interleaved with v34 reader+issuer. New distinct staged-credential fixtures exercise signed counters 0→0, 0→1 and 1→2, rejection of 2→2 and 2→1, signed BS=0→1 and BS=1→0 with stable BE, and rejection of BE mismatch or BS without BE. These were exercised by real ES256 and PostgreSQL at commit `9a3a2c70` (PostgreSQL integration PASS); commit `0f5f577c` fixes the independent gofmt failure. The draft tests now exercise **four distinct transaction-boundary fault models**. First, a synthetic application-side wrapper commits real SQL and discards the successful return. Second, a test-only `net.Conn` wrapper with the original restricted finisher role, local `sslmode=disable` PostgreSQL and genuine v35 ES256 proof watches the server's PostgreSQL `CommandComplete(COMMIT)` frame and **closes the real TCP socket before forwarding it to pgx**. The coordinator must return sanitized UNAVAILABLE without retry while an independent database query confirms one durable possession update, one nonce consumption, one audit/notice and denied replay. The post-server-COMMIT case `counter_one_to_two_tcp_commit_ack_lost` passed integration on commit `324ae5f7` (5/5 CI). **Third**, the test-only TCP wrapper can instead close the socket *before sending any COMMIT request bytes*. `counter_one_to_two_tcp_commit_request_dropped` passes on code commit `7883e70e` ([PostgreSQL integration #45345226265](https://github.com/herdifirdausss/mamony-go/actions/runs/45345226265)); the coordinator returns sanitized UNAVAILABLE while the staged credential, nonce, audit and notice remain unchanged. **Fourth**, a real loopback socket accepts the complete outbound `COMMIT` write and closes before any response is read, leaving whether the server processed it deliberately uncertain. The `counter_one_to_two_tcp_commit_write_no_response` fixture waits for the original PostgreSQL backend to terminate, then accepts **only** a wholly committed activation (including exact event/notice/nonce and denied replay) **or** a wholly rolled-back pending credential with no new effects. It must return sanitized UNAVAILABLE and never auto-retry. [PostgreSQL integration #45346536763](https://github.com/herdifirdausss/mamony-go/actions/runs/45346536763) passed on code SHA `da4ea47d`. These three TCP cuts use real restricted-role PostgreSQL and signed ES256 proofs. An outbound write accepted by the local TCP stack does **not** establish the server received or executed the request. They do not simulate arbitrary partitions during server COMMIT, database crash, standby failover or backup restore. One selected real-DB v34 reader/issuer/finisher lock interleaving is covered; exhaustive permutations, production finisher custody and restore safety remain open. No PKA-T01–T28 blanket PASS is justified.

**G4 disposable PostgreSQL crash-restart evidence (not backup/failover):** [PostgreSQL integration #45351020995](https://github.com/herdifirdausss/mamony-go/actions/runs/45351020995) passed on `92565db0` with a new step after `make integration`. The CI script `tools/postgrestest/check-passkey-crash-recovery.sh` first verifies the actual CI service identity (exact `mamony_test_ci` DSN, PostgreSQL 18.7 image, database user, container ID, `fsync=on` and `synchronous_commit=on`), then checks **9 verified credentials**, **9 linked consumed challenges**, **9 possession audit records** and **9 PENDING notices**. A stable snapshot of **all** passkey credentials, activation challenges, activation notices and possession-audit rows is taken before a Docker `SIGKILL` of the disposable PostgreSQL service container. The **same container/data volume** is started, readiness is checked, and the exact snapshot and relational counts must match. This detects loss or partial persistence of already-committed v36 evidence under this one-node crash-restart path. It does **not** test a crash during an in-flight commit, loss of the primary volume, PITR, backup restore, replication lag, failover or production recovery procedures. No additional login/recovery authority is conferred.

**G4 disposable logical backup-to-second-instance restore evidence (not PITR/failover):** [PostgreSQL integration #45373784654](https://github.com/herdifirdausss/mamony-go/actions/runs/45373784654) PASSED on code SHA `37ab47cc`, including the existing real PostgreSQL integration and SIGKILL/restart gates. After all test transactions completed, `tools/postgrestest/check-passkey-backup-restore.sh` used PostgreSQL 18 `pg_dump` to create a custom-format backup of `mamony_test_ci`. It started a **second** isolated `postgres:18.7` container with its own `mamony_test_restore` database, created NOLOGIN role identifiers needed by RLS policies, and ran `pg_restore --single-transaction --exit-on-error --no-owner --no-acl`. The same shared read-only snapshot query checked that **9 possession-verified credentials have 9 consumed challenge links, 9 possession audit events and 9 PENDING notices**, and that the complete credential/challenge/notice/possession-audit row digest matches the source. The dump is ephemeral and discarded with the test container; the source is never overwritten. The restore is intentionally **data-only authority coverage**: it does not restore/test original SQL role ownership, access grants, role passwords, independently provisioned credentials, notification delivery or production backup encryption/key custody. Critically it backs up the database **after** commit: restoring a **stale pre-commit/pre-consumption backup may resurrect consumed nonces or erase security events**. Prevention/detection of such rollback requires a separately approved external continuity/fencing and reconciliation policy. No PITR, server/volume loss, standby replication/failover or rollback-to-old-backup scenario has passed.
