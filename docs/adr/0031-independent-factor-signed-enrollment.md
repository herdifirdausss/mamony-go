# ADR 0031 — Pre-provisioned asymmetric factor for first recovery-code enrollment (Identity v28)

Status: **PROPOSED / Draft PR #68** stacked on Draft #67. No merger, deployment, public endpoint or user-controlled key registration. This candidate demonstrates a cryptographic *possession* boundary; it does **not** claim an approved production MFA/AAL2/AAL3 ceremony.

## Why another password/session is not independent possession

Mamony v25 correctly refuses to bootstrap the first five saved recovery codes using only session plus fresh Argon2id password. Those are not independently proven possession of another authenticator. Identity v28 implements **a separate public-key signing proof** that can provide independent evidence only when its signing key was **already bound to the correct account through an independently trusted provisioning ceremony**. We do not have such a ceremony: there is **no production key provisioner, webauthn origin/RP ID, hardware attestation, user verification assertion, credential-rotation UX or trusted recovery operator**. Until an account's key was genuinely provisioned out-of-band under reviewed policy, all issuance remains **default DENY**. Do not describe this as NIST AAL2 or phishing-resistant WebAuthn.

Key choice: **Ed25519**, 256-bit public key, cryptographic signature checked with Go standard-library `crypto/ed25519`. NIST SP 800-63B-4 and OWASP emphasize prior authenticator binding, fresh independent cryptographic challenge and protecting authenticator enrollment from session/password takeover. No Ed25519 keypair generation/registration route is mounted; the test ADMIN fixture alone inserts synthetic public keys.

## Proof ceremony (unmounted)

1. An **admin-preprovisioned** `recovery_code_factor_keys` row binds one 32-byte public key to an ACTIVE, verified subject's `session_epoch` and current `contact_version=1`. Only privileged owner/test ADMIN can INSERT or rebind; **every production runtime role has zero table access**. A password/contact epoch change stales the key. Revoked keys are denied.
2. The trusted `RecoveryFactorChallengeIssuer.Issue(session, email, currentPassword, peer)` checks session subject equals account authenticated by existing durable pre-Argon2id admission + real Argon2id verifier, then stages a new `RECOVERY_CODE_ROTATION` 30-second one-use grant. Dedicated `mamony_identity_recovery_factor_issuer_runtime` has only EXECUTE on `issue_recovery_code_factor_challenge`: the transaction locks grant → subject/contact → live session → prebound current public key, ensures there are **no pre-existing offline recovery codes**, consumes the grant and creates a random, unique **256-bit challenge nonce** with three-minute expiry. It cannot approve a signed challenge or mint a session/password.
3. The pre-provisioned independent authenticator signs a **domain-separated, unambiguous** payload: `mamony:identity:recovery-code-factor-challenge:ed25519:v1\x00` followed by fixed-length challenge ID, subject ID, **big-endian 8-byte session epoch**, and 32-byte random nonce. These fields bind intent to first offline recovery-code enrollment for that exact subject and epoch. This is **not WebAuthn verifier-name/origin binding**; without trusted user interaction the signature can be relayed in a phishing attempt.
4. Trusted `RecoveryFactorApprovalVerifier.Verify(challengeID, signature)` reads only active challenge metadata + current pre-provisioned public key from a separate read-only-definer SQL function, validates an Ed25519 signature **in Go**, charges a failed attempt on invalid signature (maximum five), generates an independent random 256-bit approval bearer and domain-separated SHA-256 digest, then calls `complete_recovery_code_factor_challenge`. The separate `mamony_identity_recovery_factor_verifier_runtime` can READ only one challenge through an owner-controlled function and can EXECUTE only `read`, `fail`, and `complete`; it cannot issue a challenge, read tables, register keys, mint grants or change offline codes. **The SQL verifier role itself is a trusted app-layer security boundary:** compromise of that credential can bypass Go signature verification **only for a previously issued valid challenge**; production deployment must protect and isolate it.
5. The SQL completion rechecks subject status, current epoch/contact, exact public key, signed challenge unused and unexpired, five-attempt cap, no existing recovery codes and no live conflicting approval. Then it consumes the challenge, writes a **five-minute one-use** `password_recovery_code_enrollment_approvals` digest for v25 (never the raw approval) and inserts immutable identifier-only `RECOVERY_FACTOR_APPROVED` audit in one PostgreSQL transaction. A failed audit/unique constraint rolls back. The returned approval bearer is only accessible through explicit `ForTrustedEnrollment`; regular formatting/logging/JSON refuses disclosure. v25 independently checks session+fresh password, current subject/contact/epoch, proof digest and expiration, then consumes the approval while creating exactly five raw recovery codes (digest-only persistence) atomically.

## Safety properties to verify

- Anonymous recovery link, bearer session alone, password alone, missing/revoked/stale key, invalid challenge, wrong private key, wrong subject/epoch, expired nonce, replay and sixth invalid signature cannot approve.
- Issuer and verifier are separate original-login fenced EXECUTE-only SQL roles; neither can INSERT/rebind the key; neither can use each other's functions or other Identity runtime duties. Full DB owner remains a shared trust root.
- Concurrent duplicate success has one winner because completion locks the account/challenge and sets consumed_at. Existing v25 enrollment enforces another one-use consumed approval and prevents second bootstrap.
- A password/contact change invalidates the provisioned key by epoch; a recovery-code set already created denies any further first-bootstrapping, even with an authentic key signature.
- No raw private key, signature or approval token is stored or logged; only public key, random nonce, digest, timestamps and account-bound audit.
- Integration test must use a real disposable PostgreSQL, authenticated session, real Argon2id, synthetic admin-provisioned Ed25519 key, real signature, then genuine v25 five-code enrollment, plus negative and role tests. All five workflows must succeed on final commit.

## Open decisions blocking real enrollment

This is **not a production independent authenticator enrollment workflow**: user-controlled key binding cannot be bootstrapped from only password/session. Choose and implement a previously trusted registration authority (preferably reviewed WebAuthn/passkey with real RP origin binding and user verification, or another approved cross-device/hardware enrollment ceremony), secure consent/one-time UI, key provenance, revocation and account recovery policy, signing-key custody, rate limiting, CSRF/Origin, subject/session binding at the HTTP boundary, hardware assurance classification, and security operational monitoring. Key registration without independent verification would defeat the design. The current v28 cryptographic candidate stays unmounted, and initial customer enrollment remains default DENY without a pre-bound independent key and reviewed policy.
