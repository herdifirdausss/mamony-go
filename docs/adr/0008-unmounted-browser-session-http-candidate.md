# ADR 0008 — Unmounted first-party browser session handler (Draft PR #43)

Status: **Candidate code with test-only dependencies; not registered in the running application, not deployable as a public login.** Implements the deliberately restricted HTTP behavior proposed by [ADR-0007](0007-first-party-browser-session-http-contract.md), building on [ADR-0005](0005-login-admission-before-argon2id.md) and [ADR-0006](0006-opaque-session-authority.md).

## Decision and implementation

Create a manually constructed `BrowserSessionHTTP` only inside the Identity handler module. The constructor requires an explicit **direct-TLS** HTTPS origin, a `ClientIPResolver` with *no* trusted forwarding proxies, the **concrete `*usecase.SessionLogin`** (which itself requires the concrete pre-KDF `*PasswordLoginFlow` and atomic session issuer), a `*usecase.OpaqueSessionAuthority` for resolve/revoke, and **exactly 32 bytes of separately provisioned CSRF HMAC secret**. There is **no default key**, listener registration, publicly constructible `main` wiring, runtime environment flag or inferred reverse-proxy trust. The existing public/private `httpedge` routers remain health-only; route-isolation tests assert 404 for all four candidate paths on both listeners.

All paths reject query strings, URL fragments, Authorization headers, spoofed Forwarded / X-Forwarded-For / X-Forwarded-Proto / X-Forwarded-Host / X-Real-IP / True-Client-IP identity, mismatched Host, missing direct TLS, and cross-site Fetch Metadata. Browser state-changing requests require **exactly one trusted Origin matching the configured HTTPS origin**; read-only GET may omit Origin (as normal browser GET often does) but must reject any supplied nonmatching or duplicated Origin. **No CORS** is enabled. Common security response headers: `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, strict deny-all CSP. All errors are stable, generic `application/problem+json` with no identifier, bearer, password or private DB detail. This is not a constant-time or timing-equalized HTTP implementation.

## Candidate paths and tested semantics (not mounted)

| Candidate | Behavior |
| --- | --- |
| `POST /v1/identity/login` | Rejects incoming cookies (session fixation), Authorization, wrong Origin/TLS/Host and malformed JSON. Strict capped 2048-byte JSON parser shared with existing enrollment handler rejects duplicate/unknown keys and multiple documents. Canonicalize email, resolve direct client peer, and call `SessionLogin`. An account-independent LOGIN budget is consumed **before** the 64 MiB Argon2id and verifier lookup. On definitely committed issuance, return 204 empty body with exactly one host-only `__Host-mamony_sid` cookie; 401 generic incorrect/unverified/inactive, 429 budget exhausted, 503 failure/uncertain commit. No bearer in JSON, URL, query, logs or error. |
| `GET /v1/identity/session` | Cookie-only, exact host/TLS; reject ambiguous/duplicate session cookies. Calls v10 `Resolve` and returns only `{"authenticated":true}` on success, never subject/role/email. No sliding expiry and no cookie refresh; invalid/revoked/expired 401 and SQL failure 503. |
| `GET /v1/identity/csrf` | Cookie-only, first-party no-store. Calls v10 `Resolve` **before** returning a separate signed, 15-minute, session-bound CSRF token to the same origin. Never reveals the session bearer. CSRF token itself does not authorize a financial operation. |
| `POST /v1/identity/logout` | Cookie-only, strictly empty body, exact Host/Origin/TLS and exactly one `X-Mamony-CSRF`. Verify session-bound CSRF signature **before** database lookup. Resolve session, invoke v10 idempotent Revoke, and return 204 + host-only cookie deletion using the same security attributes only on certain success. 401 invalid session, 403 invalid CSRF, 503 ambiguous/failed revocation (no false logout success claim). |

Session cookie has `Path=/`, `Secure`, `HttpOnly`, `SameSite=Strict`, **no Domain** and `Max-Age=43200` (the existing 12h absolute PostgreSQL expiry remains authoritative). Javascript cannot read the bearer. CSRF token is a *distinct* canonical unpadded base64url representation of eight-byte big-endian Unix expiry + 32-byte HMAC-SHA256. MAC domain `mamony:identity:browser-csrf:v1`, signed material includes expiry, exact trusted origin and a SHA-256 binding of the 256-bit session bearer. Expiry is 15 minutes, checked on issuance and verification using a server-side clock. The HMAC uses a distinct 32-byte secret not reused for session digests, email proof or login admission. Compare the 32-byte MAC in constant time, verify canonical base64url, prevent future-dated tokens and disallow cross-session and cross-origin replay. No unsigned double-submit token or CSRF value in URL is accepted. **Key rotation/distribution and multi-instance consistency are unimplemented operational requirements.** A stolen session bearer or an XSS-compromised first-party origin can still undermine this CSRF defense; protect delivery with TLS and a meaningful frontend CSP.

## Verification and explicit limits

Unit/httptest covers only **candidate handler behavior**: complete login→cookie→session→CSRF→logout chain; mandatory admission and password authentication before any session mint; no cookie after wrong password, quota denial, SQL outage or uncertain commit; cookie host-only prefix and secure attributes; duplicate/malformed JSON, origin/host/TLS and forwarded identity rejection; duplicate session cookie rejection; cross-origin and missing/expired/tampered CSRF and cross-session replay; logout cannot claim success before DB revocation; and no secret leaks. The route inventory test explicitly verifies that neither the public nor private server exposes these paths.

**This candidate is not production-ready.** The session DB role's `SECURITY DEFINER` issuer can mint for a known eligible subject without proving the password if its EXECUTE privilege is used directly. This is a high-priority boundary requiring network isolation/credential handling and potentially cryptographic authorization proof before public exposure. Likewise, no production CSRF HMAC key lifecycle, reverse proxy topology, browser Chromium session acceptance test, realistic WAF/global login quota, MFA/step-up, password/contact-change epoch revocation, idle/refresh/rekey policy, logout recovery/ambiguous-commit UX or finance-specific authorization is in place. App authorization MUST recheck subject/action/resource/tenant at the operation boundary; a valid session resolves an identity, never a financial permission.

**Keep stacked PR #43 Draft. Do not register the handler on public or private ingress, deploy cookie sessions, merge to main or claim production safety solely from CI passing.**

## Stacked regression evidence (#44; still not enabled)

The optional Chromium + real PostgreSQL suite `TestIdentityZBrowserSessionE2E` now exercises the manually mounted test-only login/session/CSRF/logout handler with real Argon2id, verified-email proof, pre-KDF admission and v10 transactions. The separate [browser E2E runbook](../runbooks/identity-browser-e2e.md) documents cookie storage, HttpOnly protection, same-origin fetch, cross-site rejection, CSRF replay, certain cookie deletion and the dropped-response-after-revoke case. This adds browser behavior evidence, **not** a production TLS/proxy design or an authenticated-issuance proof protecting against direct use of the database issuer role.
