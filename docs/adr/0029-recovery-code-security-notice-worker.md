# ADR 0029 — Isolated recovery-code security notice worker (Identity v26)

Status: **PROPOSED / stacked Draft PR #66**, based on Draft #65. The recovery-code lifecycle, worker and all related PRs remain **unmerged, unmounted, not deployed**.

## Decision

Creating or replacing saved offline recovery codes is a security-sensitive event; it creates an account alert obligation in v25's separate `password_recovery_code_notices` table. That queue must not be processed as a password-change notice or as a token-bearing password-recovery email. Identity v26 adds **a third, purpose-separated token-free delivery capability** with a narrowly scoped PostgreSQL role, isolated Mailgun templates, retry and count-only monitoring. **Mailgun acceptance is not verified mailbox delivery.**

`mamony_identity_recovery_code_notice_runtime` has schema USAGE and EXECUTE only on `claim_recovery_code_security_notice(lease)` and `finalize_recovery_code_security_notice(event,lease,outcome,message_digest)`. SECURITY DEFINER functions reject calls where `session_user` is not the original role, preventing SET ROLE origin substitution. The sender has no table SELECT, password verifier, recovery-code enrollment, session, recovery-approval issuance, reset redemption, webhook, audit-write, recipient-write or maintenance authority. A **different** `mamony_identity_recovery_code_notice_monitor_runtime` can call only `recovery_code_security_notice_health()`, returning five aggregate counts. The v25 manager cannot claim or inspect the sender queue; the v17 `PASSWORD_CHANGED` and v22 `PASSWORD_RECOVERED` notification principals have no cross-purpose grants.

## Delivery and integrity

The v25 transactional provenance is preserved: each queued row references an existing `security_outbox` event and the claim function rechecks `RECOVERY_CODES_ENROLLED` or `RECOVERY_CODES_ROTATED` as recorded by the manager, event/subject/timestamp match, current verified email/contact version, subject not DELETED and creation within the past 24 hours. Ineligible rows are marked DEAD **without sending**. PostgreSQL `FOR UPDATE SKIP LOCKED` plus a 45-second lease prevents two workers from claiming the same row simultaneously; the worker uses a cryptographically random lease ID and a maximum ten-second bounded provider request. Finalization is lease-fenced (including checking the lease has not expired), has a maximum of five attempts and 1/2/4/8-minute retries, and stores only SHA-256 of a canonical Mailgun Message-ID after a valid provider 200 response. Invalid acknowledgements and transient transport/provider responses are retried; permanent errors become DEAD.

The Mailgun adapter is constructed with the reviewed allowlisted-region HTTPS domain, sender domain validation, auth header, fixed timeout and redirect denial from `SecurityNoticeSender`. It sends **text-only, fixed, link-free, token-free** content and disables click/open tracking while requiring TLS. The enrollment and replacement templates differ, and the only caller-controlled input is the validated recipient/address and enum kind; no user ID, raw recovery code, code digest, challenge, bootstrap proof, password, new code quantity, session or event ID is included in the message. Raw provider failure responses never become user-facing errors or logs. An ambiguous provider submit can cause duplicate **token-free** alerts; no exactly-once guarantee exists across external email transport.

The read-only monitor reports `pending_due`, `dead`, `submitted_unconfirmed`, `retrying` and `expired_pending`—no event IDs, subject IDs, email addresses or provider message IDs. Maintenance alone may purge up to 100 notification rows older than seven days per operation, ensuring recipient PII erasure while preserving identifier-only `security_outbox` audit. No worker/monitor may purge. No provider webhook reconciliation is introduced by v26: accepted remains **submitted-unconfirmed**, not DELIVERED; use a separate future signed Mailgun webhook principal to establish provider-reported delivery/bounce/complaint status.

## Verification and limits

- V25's genuine SQL manager event produces an immutable audit and token-free queue row. Mocked HTTP Mailgun pipeline verifies **both** `ENROLLED` and `ROTATED` templates, sender basic auth and HTTPS configured origin, region/domain, tracking opt-outs, no raw secrets or links, 429 retry then 200 ACK, independent message digests, and count-only observability.
- Integration tests enforce wrong lease, expired lease, re-claim, permanent failure/dead-letter and batch-100 maintenance retention without erasing audit.
- Purpose-specific SQL roles deny SELECT/UPDATE/DELETE on PII or identity material and EXECUTE access to unrelated password-change, recovery, enrollment, webhook or notice functions. Tests prove other roles cannot claim new code-change notices and sender cannot read monitor counts.
- `Engineering baseline`, `Specialized Go tools`, `PostgreSQL integration`, `Identity browser contract` and `Identity real browser E2E` must all succeed on the **exact final PR head** before review.

**Still blocked:** live independent bootstrap approval issuer/MFA recovery enrollment, secure offline-code display, delivery-worker scheduling and key custody, Mailgun webhook event verification and rate controls, bounced-address suppression/incident routing, provider-account operational setup, on-call thresholds, anti-enumeration public HTTP boundary, and human security/release review. A DB owner can forge alerts or modify recipients; Profile A SQL runtime least privilege does not eliminate owner-compromise risk. No live mail or public account-recovery feature is activated by this proposal.
