# ADR 0027 — Two-evidence password recovery using pre-enrolled offline codes (Identity v24)

Status: **PROPOSED, stacked Draft PR #64**, based on Draft #63. **Not production-ready and NOT an approved AAL2/AAL3 authentication or MFA recovery flow.** No public code enrollment, code display, recovery UI, endpoint, scheduler, issuer, mail sender or real customer provisioning is enabled.

## Decision and security claim

Identity v21 required an independent, short-lived `password_recovery_assurance_grants` row, but it was bound only to the account and session epoch, so an approval for one email recovery challenge could inadvertently authorize a different subsequent challenge. Identity v24 **adds a nonnullable FK `challenge_id` to every grant** and rejects redemption if that ID is not the exact locked, live, email-verified challenge. Deployments with legacy unbound grants must stop and explicitly review/revoke them before upgrading: the migration intentionally fails rather than silently approving a guessed challenge.

The first candidate second recovery evidence is **a previously saved 256-bit CSPRNG offline recovery code**, shown/saved only at an earlier *separately reviewed* authenticated factor-enrollment ceremony. The verifier requires **BOTH** an unexpired 15-minute email recovery proof AND the independently stored offline code in one owner-controlled transaction. Re-sending a code to the same email account, security questions, SMS-to-same-device, a standard session cookie, a second password, or the ability to produce an email link are **not** equivalent independent evidence. The code issuer is only a pure Go generator; there is **no production enrollment command or DB permission to insert code digests**, and no API/HTML flow. Tests insert 256-bit proof digests under a privileged disposable ADMIN fixture only. This implementation therefore remains unusable for real users until an enrollment ceremony and the required MFA/assurance policy are approved.

The offline code generator uses operating-system CSPRNG to produce exactly 32 bytes encoded into canonical 43-character base64url. A purpose-separated SHA-256 digest (`mamony:identity:offline-recovery-code:v1\x00` + 32 raw bytes) is the only persisted secret-derived representation. An offline code is redacted from standard formatting, JSON, logging and text serialization. The 256-bit code is intentionally above the NIST 112-bit threshold that would require password-grade storage for shorter lookup secrets; this **does not** make the overall recovery ceremony automatically satisfy any authenticator assurance level. The enrolled code's `subject_id`, `session_epoch`, verified `contact_version` and enrollment timestamp are DB-owned: offline evidence must pre-date the email recovery challenge and match the subject/contact epoch. A changed password or verified contact invalidates the old code set, fail-closed, until a future independently approved rotation ceremony.

## Atomic verification and one-use semantics

Separate principal `mamony_identity_recovery_assurance_runtime` receives only schema USAGE plus EXECUTE on `approve_password_recovery_offline_code(recovery_digest,offline_code_digest,event_id)`. The SQL SECURITY DEFINER function checks original `session_user`; the role has **no SELECT/INSERT/UPDATE/DELETE on subjects, aliases, password verifiers, challenges, offline codes, grants, sessions, audit or notice queues**, and cannot issue an email recovery proof, reset a verifier, create a login session, or enroll a code. The caller passes two purpose-separated 32-byte digests and an opaque audit ID, never account or challenge identifiers; the subject is resolved by the unguessable email recovery digest, and all denials return a generic false.

Under locks in order subject+alias -> recovery challenge -> pre-enrolled offline code -> grant, SQL checks ACTIVE subject, current verified email/contact version, matching session epoch, unrevoked/unconsumed recovery challenge that has not expired according to **DB clock after locks**, code owned by the SAME subject/version/epoch enrolled before this challenge and not previously consumed, and absence of an already-active approval for that challenge. In one transaction it consumes the code, creates/replaces a **challenge-bound five-minute-or-remaining-challenge-lifetime (whichever is shorter)** single-use assurance grant, and inserts an identifier-only immutable `RECOVERY_ASSURANCE_APPROVED` security event. A late audit collision fails the transaction and rolls back the consumed code and grant; a disconnected client after COMMIT is an **ambiguous outcome, never an automatic retry**.

The v21 redemption function is redefined with an unchanged SQL/Go signature and original recovery-redeemer grants. It now locks and extracts `challenge_id`, requires a grant for that exact challenge, and consumes that exact grant in the same transaction as Argon2id password rotation, session epoch invalidation, recovery token consumption, `PASSWORD_RECOVERED` security audit and token-free notification obligation. An email attacker cannot produce offline evidence, and an attacker creating a different email recovery challenge after a legitimate approval cannot reuse the old grant. A stolen offline code alone cannot produce the issued email proof, and a code from another subject or changed epoch is denied.

## Threat model, operational requirements and limits

- **Mailbox compromise:** alone is insufficient; the pre-enrolled offline code must still be obtained. However a device/password manager synced to the mailbox may NOT be independent. The future enrollment UI must warn about secure offline storage and threat-specific device/channel separation.
- **Offline code loss/reuse:** each verified approval **burns** one code even if the user never redeems the password challenge. Reissuance and replacement require a separately reviewed high-assurance authenticated factor workflow plus account notification. Bulk replacement/overwriting old codes from a compromised session is forbidden by default.
- **Malicious DB writer / privileged operator:** Profile A is not a genuinely independent trust root; a database owner with table write access can mint codes and grants. The EXECUTE-only runtime isolation limits application/worker credentials but does **not** protect against full owner/DB compromise. Profile B requirements remain open.
- **Online guessing and denial:** 256-bit uniform random codes resist guessing, but release still requires per-IP/peer/device/subject admission budgets, bot protection, broad enumeration-safe response/timing, lockout-DoS protection, incident alerts, and monitoring failed approvals. No public endpoint exists in this PR, so neither rate limiting nor constant-time public UX is claimed.
- **Authenticators and AAL:** saved codes and an email proof are a particular recovery evidence combination; required AAL2/AAL3 and device-bound authenticator recovery policies must be decided separately using NIST SP800-63B-4. This PR **does not implement MFA enrollment, MFA recovery, passkey management or identity proofing.**
- **Migration:** a NOT NULL challenge FK blocks upgrade if an old unbound grant survives. This intentionally requires explicit operator review, not automatic deletion, guessing, or silent backfill.
- **Observability:** an extra identifier-only approval audit event is committed. Production notification/on-call for assurance events, code enumeration, receipt integrity and retention remain open.

## Verification contract

Real PostgreSQL integration must prove (1) no assurance from email alone, malformed offline proof or mismatched subject, (2) code enrolled before challenge, (3) one-use code and at most one active approval per challenge, (4) old grant does NOT permit a new challenge, (5) recovery redemption consumes the matching grant, (6) audit collision atomic rollback, (7) two simultaneous approvals yield exactly one winner, and (8) status/contact/epoch changes prevent stale code use. Role matrix must reject all direct table access and all other Identity roles' EXECUTE. No test disables lint, PostgreSQL RLS isolation or browser regressions.

Keep PR chain Draft/unmerged. No real account can self-recover until independent enrollment ceremony, production assurance policy/MFA decisions, anti-abuse HTTP boundary, reliable code replacement notification, deployment keys and human owner signoff are complete.
