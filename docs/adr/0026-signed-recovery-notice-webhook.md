# ADR 0026 — Signed Mailgun recovery-notice receipts and status reconciliation (Identity v23)

Status: **PROPOSED / stacked Draft PR #63**, based on Draft #62. Do not merge, deploy, mount a webhook, send live mail or permit a public recovery flow.

## Decision and separation of authority

v22 `PASSWORD_RECOVERED` alerts are token-free notifications, not recovery proofs or login grants. `ACCEPTED` means the Mailgun API acknowledged a submission, **not** that it reached an inbox. We need independently signed Mailgun event-data to distinguish `DELIVERED`, `TEMPORARY_FAILURE`, `PERMANENT_FAILURE`, `COMPLAINED` and `UNSUBSCRIBED`.

The v17 callback handles only `PASSWORD_CHANGED` alerts. Rather than granting the old webhook additional table access, v23 adds **`mamony_identity_recovery_notice_webhook_runtime`** with schema USAGE and EXECUTE **only** on `record_mailgun_recovery_notice_receipt(token_digest,event_digest,message_digest,state,event_at)`. All of the new SQL functions are owned and SECURITY DEFINER with a hard `session_user` origin check. This role cannot inspect or mutate either notice queue, recovery tokens, the assurance gate, password verifiers, sessions, aliases, subjects or old Mailgun receipts. The recovery notice sender and count-only observer likewise cannot record callbacks. A forged event routed to the v17 callback cannot update a recovery notice; a recovery-specific callback cannot update a v17 `PASSWORD_CHANGED` notice even if both synthetic rows deliberately share a Message-ID digest.

## HTTP authenticity and minimal persistence

`MailgunRecoveryNoticeWebhook` is a **distinct, unmounted** `net/http` handler that delegates cryptographic parsing to the existing reviewed `MailgunSecurityNoticeWebhook` HMAC-SHA256 verifier: require POST JSON <=16KiB; one or two explicit signing secrets for rotation (different from Mailgun Sending API key); exact configured Mailgun domain; signature over `timestamp+token` with constant-time comparison; timestamp no more than nine hours old or fifteen minutes in the future; canonical bounded provider Message-ID, event ID and event-time; suppress click/open/unrecognized event types. Bad authenticity/input returns generic 406 before any DB read/write. Only operational DB/storage failures return 503 to request legitimate Mailgun retries. **A signed callback is authenticated to the configured Mailgun signing secret, not evidence of inbox ownership**; the signing secret and HTTPS ingress must remain isolated.

The handler passes only three SHA-256 digests, an allowlisted delivery-state enum and a bounded event timestamp to `RecoveryNoticeWebhookStore`. The database stores no raw webhook body, signature, token, recipient, provider Message-ID or user data. Separate unique token and event digests prevent replay/duplicate receipt insertion; receipts may arrive **before** the sender finalizes a 200 response, so the v23 `finalize_password_recovery_notice` reads pre-existing receipts and selects the highest-precedence state. Late signed receipts advance only the matching `ACCEPTED` recovery notice, never another purpose. Severity ordering is monotonic: `TEMPORARY_FAILURE < DELIVERED < PERMANENT_FAILURE < COMPLAINED < UNSUBSCRIBED`. A late delivered callback cannot conceal a complaint or bounce. Unknown signed Message-IDs are retained only as digests for count-only unmatched observation and erased by bounded retention.

The v22 monitor ABI (five counters) is preserved. Its submitted-unconfirmed count now **excludes** delivered/permanent/complained/unsubscribed notices. A new EXECUTE-only `password_recovery_notice_delivery_health()` returns three additional counts: `delivered`, `provider_failures`, `unmatched_events`. The same independent `mamony_identity_recovery_notice_monitor_runtime` reads both functions without SELECT on receipts or PII. A maintenance-only purge removes up to 100 receipt rows older than seven days; identifier-only security audit survives. This patch doesn't schedule alerts or create dashboards.

## Verification

- Real PostgreSQL tests enforce new webhook role's exact EXECUTE boundary; test attempts by the old webhook, recovery sender, monitor, issuer, redeemer and platform roles must be denied.
- HMAC unit tests on the unmounted wrapper cover active+previous signing keys, wrong signature, wrong domain, stale timestamp, unrecognized tracking-only events, missing recorder and configuration.
- Disposable PostgreSQL integration covers a signed callback before provider ACK, restricted sender claim/finalize, concurrent duplicate deliveries, bounce vs late delivered, complaint and unsubscribe precedence, unknown signed callback, wrong signature/domain, count-only monitor, bounded receipt cleanup, audit survival, and a deliberately **shared synthetic Message-ID between `PASSWORD_CHANGED` and `PASSWORD_RECOVERED`** to prove cross-purpose isolation. No live provider or email is used.
- CI baseline, architecture, lint, security, PostgreSQL, real Chromium/browser contract must all be green on **the exact final head SHA**. No tests weakened for the result.

## Not yet production ready

Ingress/TLS trust chain, rate limiting, Mailgun account webhook configuration, independent signer-key storage/rotation, live delivery/bounce/suppression operational handling, alert thresholds/on-call escalation, retry incident response, event retention/backups, protection against webhook signing-key compromise and intentional duplicate callbacks need approval. In particular, **a compromised webhook signing credential can forge apparent provider delivery status**; do not treat this as a substitute for account authentication or recovery assurance. The default-DENY v21 assurance/MFA grant issuer remains entirely unimplemented; the reset page, token redemption HTTP API and live recovery mail delivery remain unmounted. All PRs remain Draft and unmerged.
